# Review of 2026-10-28

A full-codebase review run with the Codex CLI (gpt-6.1-sol, read-only, xhigh reasoning) after the
proofs, RPC and sync round. The findings as reported, each followed by what was done.

Regression tests live in `test/review.test.ts` (first review) and `test/review2.test.ts` (second review).

1. **Critical — Duplicate validators let one trusted key forge light-client trust.** [src/types/validator.ts:240](src/types/validator.ts:240), [src/light/client.ts:126](src/light/client.ts:126). Binary decoding accepts duplicate keys, and skipping verification counts their trusted power repeatedly. **Scenario:** one of four equal-power validators supplies a fabricated future set containing its key twice and signs a fabricated header; both quorum and overlap checks pass. Reproduced. P2p state sync uses this decoder; the tests cover only legitimate sets.

   **Resolution:** fixed: decoded sets are checked for duplicates, order, positive power and proposer index (`ValidatorSet.decode`); test

2. **Critical — The signature cache accepts corrupted signatures and splits application state.** [src/app/core/app.ts:446](src/app/core/app.ts:446). Cache hits depend on transaction body and signing address, without checking the supplied signature bytes. **Scenario:** prime some nodes with valid transaction T, then include T with a zeroed signature in a block → primed nodes execute it, cold nodes reject it, and their roots differ. Reproduced. The existing forged-signature test corrupts before priming the cache.

   **Resolution:** fixed: the cache binds the hash of the signature bytes; test

3. **Critical — Signature preverification makes ordinary authority updates depend on mempool history.** [src/app/core/app.ts:197](src/app/core/app.ts:197). All keys are resolved before any transaction executes, while cache hits bypass that resolution. **Scenario:** T1 installs a new active key and T2 spends using it; a node that checked both pending transactions executes both, while a cold node rejects T2 against the old authority. Reproduced with different roots for identical valid block bytes.

   **Resolution:** fixed: keys are resolved per transaction as the block executes, and checkTx waits behind a block in progress; test

4. **High — Re-proposing a locked block under another proposer can permanently halt consensus.** [src/consensus/consensus.ts:345](src/consensus/consensus.ts:345). Re-proposals retain the original block’s proposer address, but admission requires the current round’s proposer address. **Scenario:** obtain a polka, time out without a commit, and lose the original proposer → the next honest proposer’s re-proposal is rejected, including locally. Reproduced with three connected honest validators stuck at height 1.

   **Resolution:** fixed: a proposal is accepted from the round's proposer whatever proposer address the (re-proposed) block carries

5. **High — Restarting at an unfinished height can deadlock behind the signing guard.** [src/consensus/consensus.ts:285](src/consensus/consensus.ts:285). Consensus restarts at round zero, creates different proposal bytes, and schedules no proposal timeout when signing is refused. **Scenario:** persist a proposal, crash before committing, and restart a single-validator chain → the new timestamp conflicts with the stored proposal and consensus remains in `propose` indefinitely. Reproduced; the recovery test restarts one validator while others advance.

   **Resolution:** fixed: after a restart consensus resumes in the round after the one the guard already signed in; test

6. **High — An ordinary peer can force billions of synchronous proposer iterations before authentication.** [src/consensus/consensus.ts:344](src/consensus/consensus.ts:344). `proposerAt(p.round)` runs before proposal signature verification, and its cost is linear in the supplied round. **Scenario:** send a proposal for the current height with `round = 4294967295` and `polRound = -1` → the main thread performs billions of BigInt iterations before examining the signature.

   **Resolution:** fixed: proposals and votes more than 1000 rounds ahead are ignored

7. **High — Valid staking amounts can overflow serialized shares and halt finalized-block execution.** [src/app/core/staking.ts:102](src/app/core/staking.ts:102), [src/app/core/types.ts:363](src/app/core/types.ts:363). Shares are multiplied by \(10^6\), but remain serialized as u64 without admission bounds. **Scenario:** delegate `20000000000000` base units at the initial exchange rate → `checkTx` succeeds, then `root()` throws `u64 out of range` after the block has been decided. Reproduced.

   **Resolution:** fixed: share scale 10^3 and overflow guards in bond and reward; test

8. **High — State sync trusts unauthenticated proposer priorities.** [src/sync/statesync.ts:185](src/sync/statesync.ts:185). Imported sets are checked only by a hash that deliberately excludes priorities and the proposer index. **Scenario:** a snapshot peer supplies genuine keys and powers with altered priorities → the joining validator accepts them and derives different future proposers, rejecting legitimate proposals or proposing out of turn. Enough affected joining voting power can halt the chain.

   **Resolution:** mitigated: the sets for H and H+1 must pick the proposers the chain actually used at their commit rounds; the residual is documented

9. **High — Key rotation lets validators escape or misattribute later evidence.** [src/app/core/evaluate.ts:199](src/app/core/evaluate.ts:199), [src/app/core/staking.ts:390](src/app/core/staking.ts:390). Rotation removes the old address mapping, while punishment resolves historical evidence through the current mapping. **Scenario:** double-sign with key A, rotate to B, then receive valid evidence for A → no validator is found and punishment is skipped. Reproduced. Reusing A for another validator instead redirects punishment there.

   **Resolution:** fixed: every consensus key a validator ever used is recorded (type 13) and resolves evidence; keys are never reusable; test

10. **High — Queue slashing overlooks stake that still supplies voting power during the H+2 delay.** [src/app/core/staking.ts:345](src/app/core/staking.ts:345). Entries created at or before the infraction height are excluded. **Scenario:** undelegate substantial stake at H, double-sign at H+1 while that stake still contributes to the signing set, and receive evidence at H+2 → the unbonding entry is exempt because its creation height precedes the infraction.

   **Resolution:** fixed: entries from the height before the infraction are slashed too; test

11. **High — Redelegate followed by undelegate bypasses source-validator slashing.** [src/app/core/staking.ts:355](src/app/core/staking.ts:355). Redelegation punishment only takes funds from a current destination delegation. **Scenario:** after an infraction, redelegate A→B, then fully undelegate from B before A’s evidence arrives → the destination delegation is absent, so the slash is skipped and B’s unbonding entry remains intact. Reproduced: all 1,000 tokens survived the source slash.

   **Resolution:** accepted: same gap as Cosmos; documented

12. **High — Swapping authenticated keys within one block can prevent every affected node from restarting.** [src/db/database.ts:606](src/db/database.ts:606). History rebuilding interleaves deletion and insertion per object, so a later deletion can erase another object’s newly inserted key. **Scenario:** rotate validator keys A→temporary, B→A, temporary→B in one block → restart throws “rebuilt index does not match the live one.” Reproduced at the database layer. Tests cover undoing swaps, but not rebuilding their history.

   **Resolution:** fixed: a version's drops precede its puts in the rebuild; test

13. **High — Aborting an HTTP request body can terminate the node.** [src/rpc/server.ts:80](src/rpc/server.ts:80), [src/rpc/server.ts:148](src/rpc/server.ts:148). Body-read errors escape `handle()`, whose promise is discarded by the server callback. **Scenario:** begin a POST and disconnect during body upload → an unhandled rejection reaches Node’s default process-termination behavior. Confirmed that body-iterator errors escape the handler.

   **Resolution:** fixed: request errors are caught and the request destroyed; test

14. **High — Fetch responses allow unbounded socket buffering without scoring the requester.** [src/node/node.ts:259](src/node/node.ts:259), [src/p2p/tcp.ts:60](src/p2p/tcp.ts:60). Repeated requested hashes are served individually, and `socket.write()` backpressure is ignored. **Scenario:** repeatedly request 10,000 copies of a known pending transaction while barely reading responses → queued response buffers grow until memory exhaustion; these valid messages incur no misbehavior points.

   **Resolution:** fixed: fetches are deduplicated and capped at 256, oversize scored; a peer with 32 MB unread is dropped

15. **High — Block construction can repeatedly propose blocks exceeding its own size limit.** [src/consensus/consensus.ts:303](src/consensus/consensus.ts:303). The fixed 64 KiB reservation does not account for actual commit and evidence sizes. **Scenario:** fill the transaction budget and supply 100 valid pending evidence records → every honest proposer constructs an oversized block that validation rejects. No trimming occurs, and absent commits the mempool is never rebuilt to remove expired transactions.

   **Resolution:** fixed: the block is measured without transactions and the remainder given to them; evidence capped at 16 per block

16. **High — The signing guard’s rename lacks a directory durability barrier.** [src/store/files.ts:13](src/store/files.ts:13). The temporary file is fsynced, but the parent directory is not synced after replacement. **Scenario:** on a filesystem that loses an unflushed rename after power loss, a broadcast signature survives externally while the guard reverts to its older record, permitting a conflicting signature after restart. The missing barrier is confirmed; actual power-loss behavior was not reproduced.

   **Resolution:** fixed: the directory is fsynced after the rename

17. **Medium — Snapshot-height blocks and backfilled blocks are stored without authenticating their bodies or commit signatures.** [src/sync/statesync.ts:179](src/sync/statesync.ts:179), [src/sync/blocksync.ts:278](src/sync/blocksync.ts:278). Header-hash checks do not establish that supplied transactions, evidence, or commits match that header. **Scenario:** preserve a genuine header but replace its transactions and commit → fabricated content is persisted and indexed. Reproduced through backfill; subsequent inclusion proofs correctly fail.

   **Resolution:** fixed: snapshot-height and backfilled blocks are checked body against header and commit against the signing set

18. **Medium — Repeated raw transactions overwrite successful locations and break result proofs.** [src/store/blockstore.ts:90](src/store/blockstore.ts:90), [src/node/node.ts:362](src/node/node.ts:362). One global location per hash cannot reconstruct per-position execution results. **Scenario:** include `[T, T]` → execution results are success then duplicate failure, but the index retains only the failure and `queryTx` reconstructs two failures. Reproduced: RPC reports failure and its result proof fails verification.

   **Resolution:** fixed: results are stored per block and the first position of a repeated transaction owns its index entry; test

19. **Medium — RPC queries expose speculative state and label current values with historical heights.** [src/rpc/methods.ts:181](src/rpc/methods.ts:181). Several methods use live indices and objects, while their requested height affects only the proof or response label. **Scenario:** admit an uncommitted transfer, then request `account` at committed height H → balances include the pending transfer while the response and name proof refer to H. Validator, delegation, key, and account-list queries have related live-view inconsistencies.

   **Resolution:** fixed for account, validator and delegation; accounts list still scans live names

20. **Medium — A valid chunk for the wrong request can abort state sync instead of being retried.** [src/sync/statesync.ts:153](src/sync/statesync.ts:153). Chunk verification checks membership in the manifest but does not bind the embedded chunk to the requested job. **Scenario:** answer a request for chunk 0 with matching outer response fields but valid embedded chunk 1 → it is counted as completed, later imported twice, and the missing chunk causes a fatal root mismatch despite honest sources being available.

   **Resolution:** fixed: a chunk must match the request it answers

21. **Medium — Precommits arriving during application execution are lost from the fuller stored commit.** [src/consensus/consensus.ts:428](src/consensus/consensus.ts:428), [src/node/executor.ts:102](src/node/executor.ts:102). Updating the commit is discarded until executor state advances, and the accumulated vote set is not flushed afterward. **Scenario:** the fourth precommit arrives while asynchronous finalization is running → it is accepted but never stored, so the next block can penalize that signer as absent. The fuller-commit test delivers its vote after execution finishes.

   **Resolution:** fixed: the commit is stored again after the block is applied

22. **Medium — Unbonding changes are not coupled to evidence and light-client trust limits.** [src/app/core/staking.ts:410](src/app/core/staking.ts:410), [src/light/client.ts:76](src/light/client.ts:76). Governance replaces application parameters while engine evidence age and the default four-day trusting period remain independent. **Scenario:** adopt one-day unbonding → withdrawn validators’ old keys remain trusted for four days, and seven-day evidence can arrive after their funds have already been released.

   **Resolution:** fixed: the engine's evidence age follows the unbonding period after every commit; the light client's trusting period remains the client's choice

23. **Medium — The account CLI’s “verified” name proof has no trusted-chain anchor.** [src/cli.ts:299](src/cli.ts:299). It verifies against an app hash supplied by the same RPC server without checking that header’s commit or the light-client anchor. **Scenario:** a malicious RPC supplies a fabricated account tree, matching proof, and fabricated header → the CLI prints “name proof verified” for invented chain state.

   **Resolution:** fixed: the CLI verifies name proofs through the light client against its own anchor

24. **Medium — Transaction verification does not bind the proof to the requested transaction hash.** [src/cli.ts:346](src/cli.ts:346). The returned proof is verified independently of the CLI’s `hash` argument. **Scenario:** request verification of nonexistent or failed transaction X, and have the RPC substitute a genuine successful transaction Y with valid proofs → the CLI prints a successful verification for the request.

   **Resolution:** fixed: the CLI checks the returned proof is for the hash it asked about

25. **Medium — SSE replay performs unbounded synchronous work and buffering.** [src/rpc/server.ts:230](src/rpc/server.ts:230). Replay scans every retained height without a replay limit, rate charge, yielding, or write-backpressure handling. **Scenario:** open streams with `Last-Event-ID: 0` against a long archive and read slowly → repeated full-history serialization blocks consensus and queues large response buffers.

   **Resolution:** fixed: replay is capped at 1000 blocks, charged against the rate budget (a stream asking for a replay it cannot afford is refused with 429 instead of opening with a gap), and stops on backpressure

26. **Medium — Keystore updates can destroy all previously stored keys on interruption.** [src/wallet/keystore.ts:110](src/wallet/keystore.ts:110). Every save directly truncates and rewrites the only keystore file. **Scenario:** interrupt an `add` or `remove` during the write → the JSON may be empty or partial, making every previously encrypted seed unavailable, not just the key being changed.

   **Resolution:** fixed: the keystore is written temp-fsync-rename

27. **Medium — The core asset can be issued outside the staking mint.** [src/app/core/evaluate.ts:159](src/app/core/evaluate.ts:159). `assetIssue` treats the core asset as an ordinary issuer-controlled asset. **Scenario:** the genesis core issuer issues more core tokens while inflation is zero → supply increases through a transaction, contradicting STAKING.md’s mint-only supply invariant and allowing additional stake creation up to max supply.

   **Resolution:** fixed: the core asset cannot be issued; test

28. **Low — Failed transactions can leave successful-looking virtual history entries.** [src/app/core/history.ts:127](src/app/core/history.ts:127). Virtual entries bypass the transaction’s discardable history buffer. **Scenario:** execute `unjail` followed by an operation that fails in the same transaction → database rollback restores the jailed status, but commit persists and streams the virtual `unjail` entry.

   **Resolution:** fixed: virtual entries inside a transaction follow its outcome; test

29. **Low — Zero-version retention retains every sparse-tree version internally.** [src/db/smt.ts:130](src/db/smt.ts:130). Pruning runs only when retention is positive. **Scenario:** configure `retainVersions: 0` to keep only current proofs → every block still retains another root pointer, and changed historical paths remain reachable indefinitely, causing unbounded memory growth.

   **Resolution:** fixed: pruning runs at any retention; test

Strongest parts: strict binary decoding, signature domain separation, and domain-separated Merkle hashing.  
The basic H+2 set pipeline and deferred state/result commitments are clear and consistently implemented.  
Object, sparse-key, and range proofs have substantial tamper, historical-version, and reconstruction coverage.

## Found while confirming the suite after the fixes

30. **High — block sync recursed between `check()` and `drain()`.** `src/sync/blocksync.ts`. After the stage-3 rewrite, `drain()` re-ran `check()` unconditionally and `check()` ran `drain()` again. With nothing in the buffer the drain never reached an `await`, so every peer status message during a sync recursed synchronously until the stack overflowed. The overflow surfaced as a swallowed rejection (`Exception in PromiseRejectCallback`), so the sync tests still passed.
   **Resolution:** fixed: `drain()` re-checks only after a block left the buffer; test counts the state reads of one unanswerable status (7492 before, a handful after).

31. **Medium — an event stream asking for a replay it could not afford opened with a gap.** `src/rpc/server.ts`. Charging the replay (finding 25) made an unaffordable replay silently skip, so the client saw a live stream and believed itself caught up. The rpc test then spun forever on a finished stream: awaiting an already-finished reader never yields to timers, so the test timeout could not fire and the suite hung.
   **Resolution:** fixed: the rate check runs before the headers and refuses with 429; the test reads with a guard against ended streams and asserts the 429.

## Found by the benchmarks

32. **High — a block not seen through the mempool was verified one signature at a time.** `src/app/core/app.ts`. The fix for finding 1 resolved keys per transaction as the block executes, which also moved verification into that loop, so the worker pool received one job at a time: a cold block ran at single-thread speed (930 transfers/s) and block sync with it. The two concerns are separable: a cache entry records that a signer signed a body, which no state change can invalidate, so all of a block's uncached signatures can be verified in one batch first, with the per-transaction pass still resolving each signer against the state its transaction applies to.
   **Resolution:** fixed: `prewarmSignatures` batches the block before the loop (5,100 transfers/s cold on 11 threads; the warm path is unchanged). Existing tests cover warm and cold agreement.

33. **Medium — a request sent the instant a peer connected could be dropped by the other side.** `src/p2p/network.ts`. The dialing side is established as soon as it sends `auth`; the accepting side still awaits the verification of that signature, during which its connection had no frame handler. Block sync asks for blocks from the first peer it sees, so a joining node's first request vanished and it waited out a five-second timeout before retrying elsewhere.
   **Resolution:** fixed: frames received during a handshake step are held (at most 64) and delivered once the peer is established; a test with a slow verifier sends on `onPeer` and sees the message arrive.

34. **Low — the worker verifier let the process exit while a caller awaited it.** `src/crypto/verifier.ts`. Workers were unreferenced for life, so a process whose only pending work was a verification (a CLI, a benchmark) exited with an unsettled promise.
   **Resolution:** fixed: a worker is referenced while it has jobs in flight and unreferenced when idle.
35. **High — a genesis over 512 MB could not be loaded at all.** `src/types/genesis.ts`, `src/app/core/genesis.ts`. The application state was embedded as one string inside `genesis.json` and parsed with `JSON.parse`; V8 refuses strings over 512 MB, and a document that fits still needed several times its size in heap. A genesis of a few hundred thousand accounts (two 1312-byte keys each) is well over that.
   **Resolution:** fixed: `genesis.json` may name an `appStateFile`; the application reads it as a token stream with `stream-json`, assembling one account at a time, so memory holds the objects and never the text; the node does this once, when its store is empty. The genesis benchmark loads a gigabyte this way.

36. **Medium — the encoded bytes of every object changed by a version were kept until the next root.** `src/db/database.ts`, `src/app/core/app.ts`. The change list a store writes was retained by the database afterwards: after genesis a second copy of the whole state, and after a restart (where the root is recomputed over every object to check the stored app hash) the same again, for nothing. The genesis benchmark showed it as 500 MiB per gigabyte of genesis.
   **Resolution:** fixed: the application drops the list once persisted, and the reopen path drops it once the root is checked; a test asserts both.


## Found while documenting

Writing the part-by-part tutorial (docs/tutorial/) meant reading every file against the design
record and the specifications. These are what that reading turned up, with what was done.

37. **High — a block re-proposed with a proof of lock was checked for clock drift against the current time.** `src/consensus/consensus.ts`. Every proposal went through the timeliness check, including a re-proposal of a block that already had a polka, whose time was set by its first proposer. A round that stalled longer than the drift limit (15 s by default) could then never decide that block: the locked validators prevote nil for it, no other block can gather a polka against their locks, and the height stalls for good. CometBFT applies timeliness only to fresh proposals (`polRound == -1`).
   **Resolution:** fixed: the drift check applies to fresh proposals alone; a network test stalls round 0 of two heights with a lost proposal and a lost precommit under a 300 ms drift limit and sees the re-proposal decide.

38. **Low — a transaction refused as full after its check was remembered as seen.** `src/mempool.ts`. The seen cache was written before the check (so a concurrent duplicate is checked once); when the pool filled during the check the transaction was refused but stayed cached, and a resubmission heard `seen` until the cache rolled over.
   **Resolution:** fixed: the late refusal forgets the hash; test.

39. **Medium — a decided height was written to the block store in four transactions.** `src/node/executor.ts`, `src/store/blockstore.ts`. DESIGN.md section 4 says block, commit and state land in one transaction; the code wrote the block, the next set, the set by height and the state separately. A crash between them left a block and its transaction index entries without the state that goes with them; a different block decided for that height on restart would overwrite the block but not every index entry.
   **Resolution:** fixed: the block store has `batch()`, and the executor saves a height inside one; test counts the store's transactions.

40. **Medium — a failed verification worker took the whole pool with it, and `close()` left callers waiting.** `src/crypto/verifier.ts`. A worker error rejected every pending job of every worker and the dead worker stayed in the rotation, so later jobs sent to it never completed; `close()` terminated workers without settling what they still held.
   **Resolution:** fixed: a failed worker rejects only its own jobs and is replaced; `close()` rejects what is pending; test.

41. **Low — a string beginning with a byte-order mark did not decode to what was encoded.** `src/codec/reader.ts`. `TextDecoder` strips a leading U+FEFF by default, so the codec was not a bijection on such strings.
   **Resolution:** fixed: the decoder keeps the mark; test.

42. **Low — a virtual history entry raised inside a transaction always named operation 0.** `src/app/core/history.ts`. An unjail in the third operation of a transaction was recorded against the first.
   **Resolution:** fixed: the recorder is told which operation is running.

43. **Medium — the light client accepted an anchor older than the trusting period.** `src/light/client.ts`. `trust()` checked the hash and the commit but not the age, so a stale anchor was accepted until the first verification step; a set that had since unbonded could have signed it.
   **Resolution:** fixed: an anchor outside the trusting period is refused; test.

44. **Medium — after a restart, a past-height proof for an object type that nothing changed in the window threw.** `src/db/database.ts`, `src/db/merkle.ts`. Reloading history lowered a tree's version floor only when the record named that tree; a type untouched in every retained version kept its floor at the restart height, so `proofAt` for it at any earlier height was refused although `lowestVersion` admitted the height. Accounts on a quiet chain are exactly such a type.
   **Resolution:** fixed: loading a record lowers every tree's floor, since a tree the record does not name was unchanged and its later state is also its state then; test reopens a store and proves an account and a balance at a past height.

45. **Low — one chunk timeout marked a snapshot source bad for the whole join.** `src/sync/statesync.ts`. A transient timeout counted like a corrupt chunk; with two sources, one slow reply aborted the join.
   **Resolution:** fixed: a source is dropped after three failures; a bad chunk still costs it at once.

46. **Low — backfill never asked a peer again once it had declined one old block.** `src/sync/blocksync.ts`. A peer that was itself still syncing was written off for good.
   **Resolution:** fixed: when every peer has declined, the list is cleared after thirty seconds and backfill tries again.

47. **Low — smaller fixes.** IPv6 addresses in brackets were accepted by the peer database but not parsed by the TCP transport (`src/p2p/tcp.ts`); the in-memory transport's `close()` removed the listener under its own address instead of the bound one (`src/p2p/memory.ts`); an event stream accepted unknown event types silently and rate-limit buckets were never evicted (`src/rpc/server.ts`); a newly connected peer was not told about pending evidence, which RPC-SYNC-PROOFS.md section 4.4 promises (`src/node/node.ts`); the `tx` command asked for a proof it did not use and `keys list` created a keystore when none existed (`src/cli.ts`); the toy application's snapshot was not written atomically (`src/app/kvstore.ts`); the fallback propose timeout ignored the round's delta (`src/consensus/consensus.ts`). All fixed.

48. **Dead code and names.** `Consensus.onDecision` and its listener list had no caller; `validate.ts` re-exported `blockHash` for nobody; the evidence pool's `evidenceHash` shared its name with the header's `evidenceHash` in `types/block.ts` while hashing something else. Removed, removed, renamed to `evidenceId`. A staking test compared the community pool with itself (`pool >= pool + T(10) - T(10)`); it now asserts the exact movement.

49. **Specifications brought back in line with the code.** STAKING.md: the redelegation and signing-info fields, `inflationPpb` for `inflationBps`, `SHARE_SCALE = 1000`, the downtime set (`expectedSigners`) and the slashing window (`creationHeight >= height - 1`). RPC-SYNC-PROOFS.md: the history key prefixes and the slash entry, which calls are costly, the snapshot message names, the `snapshots` RPC stub, where the transaction-proof verifiers live, and what block sync does on a timeout and when it asks for a block. DESIGN.md: the peer database fields, scoring, the dynamic properties, where validators come from, authenticated indices in the type leg, and two simplifications added to section 10 (the lock is not kept across a restart; the node's default verifier is inline). Comments: `genesis.ts` (which amounts are whole tokens), `lmdb.ts` and `app.ts` (the CLI no longer reads the store), `keys.ts` and `index.ts` (the B+ tree file's name).

Noted and left as they are, each a judgement for later: the transaction index keeps one location per hash chain-wide, so a transaction that failed in one block and succeeded in a later one points at the later one, and pruning that later block removes the entry; a `txsRoot` proof binds the tree height but not the exact count; `Node` defaults to the inline verifier; the evidence pool's hash sets are pruned only by age; `loadSnapshot` does not check that every registered type has a section; `openDB` on a missing name in a read-only LMDB environment returns undefined; `Keystore.remove` has no command; the RPC's `key`, `account` and `delegation` answer from the live indices with a proof at the requested height (finding 19); `validator` and `balance` take no height; a JSON-RPC batch is charged one token; the ping carries no clock offset; several decode paths accept out-of-range numbers that consensus bounds later; the tests chapter lists the suite's weaker assertions.


## Second review (Codex, per module)

After the first round's fixes, the benchmarks and the tutorial, the codebase was reviewed again,
this time one module per reviewer (engine, network and sync, database and store, application,
RPC and CLI, documentation, tests), each told what the specifications and the tutorial claim and
asked to check the code against them. Reviewers reproduced findings with probes where they
could. What follows is each finding as reported and what was done; the module reviews' remarks
on the documentation were folded into the specifications and the tutorial (see the end).

### Engine

50. **High — a vote for the next height was verified against one set and counted with another.** `src/consensus/consensus.ts`. Votes arriving early for H+1 were checked against the set the node happened to hold for H+2 and then replayed into H+1's round, where their index named a different validator with different power. **Resolution:** fixed: early votes are verified against the set of their own height, buffered together with the public key that verified them, and replayed only if that key still holds the index when the height begins; test.

51. **High — later-round gossip left out the polka votes a re-proposal needs.** `src/consensus/consensus.ts`. Periodic gossip re-sent the current round's votes only; a validator that missed the prevotes of the valid round could never accept the re-proposal that cites it, and with one silent validator the height could stall for good. **Resolution:** fixed: gossip also re-sends the prevotes of `validRound`.

52. **High — a relay could poison a round by attaching another body to a genuine signed proposal.** `src/consensus/consensus.ts`. The proposal's signature covers the header; a body that did not match the header was rejected, but only after the round had recorded that a proposal arrived, so the genuine one was then ignored. Bad proposal signatures also went unscored. **Resolution:** fixed: a body that does not match its header is dropped without recording the round and the relay is scored 20; a bad signature scores 20 like a bad vote; `bodyMatchesHeader` moved to `validate.ts`.

53. **Medium — the periodic re-send of a re-proposal named the block's builder, not the round's proposer (finding 4, incomplete).** `src/consensus/consensus.ts`. The header keeps the address of whoever first proposed the block; a later round's proposer re-proposing it never re-sent it. **Resolution:** fixed: the re-send is keyed on `proposerAt(round)`.

54. **High — a restarted node used genesis's evidence age until the next commit (finding 22, incomplete).** `src/node/node.ts`. The limit was refreshed from the staking parameters on commit only. **Resolution:** fixed: refreshed right after the executor opens.

55. **Medium — a valid proposal for one hash kept the node from fetching the block that had the precommit quorum.** `src/consensus/consensus.ts`. The quorum fetch and `handleFetchedBlock` refused to replace a proposal already held. **Resolution:** fixed: a fetched block for the quorum's hash replaces a different valid proposal.

56. **Medium — evidence and commit overhead could still exceed the block limit (finding 15, incomplete).** `src/consensus/consensus.ts`. Transactions were chosen against the limit, but the shell with its evidence was not. **Resolution:** fixed: evidence is trimmed until the shell fits `maxBlockBytes - 1024`.

57. **High — two signing guards over one store could sign conflicting votes.** `src/consensus/privval.ts`, `src/node/node.ts`. Each guard cached the last record independently, so two nodes started on one data directory could both sign. **Resolution:** fixed at the node: a data directory is locked (`LOCK` file with the PID plus an in-process set), and a second node on it is refused; test.

58. **Medium — the test application accepted validator updates that halted execution once decided.** `src/app/kvstore.ts`. A removal of an unknown validator passed `checkTx` and threw in `finalizeBlock`. **Resolution:** fixed: the application tracks validators, refuses unknown removals and coalesces updates per key; test.

59. **Medium — accepted validator powers could produce priorities that cannot be persisted.** `src/types/validator.ts`. **Resolution:** fixed: `MAX_TOTAL_POWER = 2^60` is enforced in the constructor; test.

60. **Low — a transaction whose check threw stayed marked seen; a lone surrogate changed on encoding.** `src/mempool.ts`, `src/codec/writer.ts`. **Resolution:** fixed: the cache entry is deleted when `checkTx` throws; `string()` refuses ill-formed strings; tests.

61. **Medium — a verification worker that exited with code 0 (as `terminate()` does) left its jobs hanging (finding 40, incomplete).** `src/crypto/verifier.ts`. **Resolution:** fixed: any exit while the pool is open fails that worker and its jobs, and it is replaced; test terminates a busy worker.

### Network and sync

62. **High — inbound handshakes bypassed the connection limit, and a failed dial left its connection open.** `src/p2p/network.ts`. The limit counted established peers only, so a flood of half-done handshakes passed it; the dial's catch path forgot to close. **Resolution:** fixed: handshakes in progress count toward `maxInbound`; a failed dial closes the connection.

63. **High — address gossip grew the peer database without bound.** `src/p2p/peerdb.ts`. **Resolution:** fixed: `MAX_RECORDS = 4096`; test.

64. **High — an advertised address could suppress honest dialing and poison bans.** `src/p2p/network.ts`. The dial exclusion set and the ban path trusted an inbound peer's `listenAddr`, so a peer could claim a seed's address to stop us dialing it, or get it banned. **Resolution:** fixed: only addresses we dialed are excluded or banned; an advertised address is a claim, not an identity.

65. **Medium — inventory fetches were neither batched to the serving side's limit nor remembered.** `src/node/node.ts`. **Resolution:** fixed: a hash is fetched once while a fetch is outstanding (10 s expiry, cleared on `item` and `itemNotFound`), in batches of 256.

66. **Medium — state sync counted a height offered twice by one peer as two sources, did not bind served headers to the height asked for, gave up on the first bad commit, and refused re-proposed blocks (findings 8 and 17, incomplete).** `src/sync/statesync.ts`, `src/light/client.ts`. **Resolution:** fixed: a height counts once per peer; the light client requires `header.height` and `commit.height` to equal the requested height; the block and its commit are fetched together and a bad one scores the source 50 and moves on; the proposer check accepts the proposer of any round up to the commit round; tests.

67. **High — block sync kept stale buffer entries, could answer with more than a frame, skipped its retry after a decline, and fought block retention.** `src/sync/blocksync.ts`. Consensus could decide heights the buffer still held; sixty-four full blocks exceed the 32 MiB frame; a declined backfill request returned before scheduling the next; backfill fetched below the retention floor and pruning deleted it again. **Resolution:** fixed: stale entries are discarded in `drain()`; responses stop at 16 MiB; rescheduling happens in `finally`; backfill stops at the retention floor.

68. **High — pruning removed blocks that still-valid evidence could name.** `src/node/executor.ts`. Evidence verification needs the validator set and time of its height, which the executor reads from the stored block. **Resolution:** fixed: pruning keeps every block whose time is within the evidence age of the last block, whatever `retain.blocks` says; test. A node that joined by state sync had no blocks before its join height, so evidence older than its join could not be checked by it; worse, the executor silently left such evidence out of what it handed the application, which would have diverged that node's state from every other's. Fixed in the third pass (below): state sync fetches the headers of the evidence window, and the executor halts rather than omits.

69. **Low — a newly connected peer was told about only the first 100 pending pieces of evidence (finding 47, incomplete).** `src/node/node.ts`. **Resolution:** fixed: all of them, in inventories of 256.

70. **Medium — `stop()` before `start()` leaked the network, and shutdown closed storage under a block still being applied.** `src/node/node.ts`. **Resolution:** fixed: the network is stopped whenever it was started (a state-sync join starts it), and `stop()` awaits `executor.idle()` before closing the environment.

71. **Medium — TCP reassembly copied the whole partial frame on every fragment; the in-memory transport delivered the sender's own buffer.** `src/p2p/tcp.ts`, `src/p2p/memory.ts`. **Resolution:** fixed: chunks are joined once the whole frame has arrived; the memory transport delivers a copy.

72. **Medium — an interrupted snapshot installation cannot be retried.** `src/sync/statesync.ts`. The application state is committed before several chain-store writes; a crash between them leaves a nonempty application store the next attempt refuses. **Resolution:** fixed in the third pass: `KvEnv.transaction` runs the install's writes to both stores as one LMDB transaction (every store of an environment shares its write transaction, and a store's own write inside it becomes a child), so a crash leaves either a complete join or nothing, and a restart simply joins again.

### Database and store

73. **High — dense-tree chunk addressing truncated 48-bit positions to 32 bits.** `src/db/merkle.ts`. `j >>> 10` and `j & 1023` on a position above 2^32 landed in the wrong chunk, so roots depended on the order of the dirty set. **Resolution:** fixed: `Math.floor(j / CHUNK)` and `j % CHUNK`.

74. **Medium — an instance number above 2^32 - 2 became an ordinary array property and vanished from exports.** `src/db/index.ts`. **Resolution:** fixed: `MAX_INSTANCE` is enforced on insert, so an instance is always a dense array index.

75. **Medium — at zero retention the dense tree still kept a size record per version (finding 29, counterpart).** `src/db/merkle.ts`. **Resolution:** fixed: the records are cleared.

76. **Medium — manifest verification accepted a manifest missing a type section, so an accepted manifest could abort the import.** `src/app/core/snapshot.ts`. **Resolution:** fixed: `verifyManifest` requires every registered type exactly once, in order; state sync passes the type list.

77. **Low — `prefixEnd` could include keys outside the prefix; memory-store reads exposed stored buffers; directory-sync errors were swallowed (finding 16, incomplete).** `src/store/kv.ts`, `src/store/files.ts`. **Resolution:** fixed: `prefixEnd` drops the bytes after the one it increments; `get` and `range` return copies; only the errors a filesystem raises for an unsupported directory sync are ignored.

78. **Medium — records are frozen one level deep, and sparse-tree proofs hand out buffers of committed versions.** `src/db/database.ts`, `src/db/smt.ts`. A caller that mutates a nested authority or a proof's sibling can corrupt what the database thinks it holds. **Resolution:** fixed in the third pass: records are frozen all the way down (`deepFreeze`, measured at 0.77 µs per account-sized record against 0.06 µs for the shallow freeze), and the sparse tree's roots, lookups and proofs are copies. Byte arrays cannot be frozen in JavaScript and remain the one thing a caller must not write into.

### Application

79. **High — the signature cache held one signature per body and key, so a second valid signature split state (finding 2, incomplete).** `src/app/core/app.ts`. ML-DSA signatures are not unique: a hedged signature over the same body is also valid, and a node that had cached one rejected the other as corrupted while a cold node accepted it. **Resolution:** fixed: the cache maps body and key to the set of signatures verified; test signs one body twice and has both accepted.

80. **Medium — a delegation could take tokens while issuing no shares.** `src/app/core/staking.ts`. **Resolution:** fixed: refused with `delegation is worth no shares at this exchange rate`; test.

81. **High — a validator slashed to zero tokens with shares outstanding crashed the reward payout.** `src/app/core/staking.ts`. **Resolution:** fixed: `reward()` returns false for such a validator and the payout skips it.

82. **High — unbonding collateral matured in the very block that carried the evidence against it (finding 10, incomplete).** `src/app/core/staking.ts`. Queues matured before misbehavior was handled. **Resolution:** fixed: `beginBlock` runs expiry, mint, rewards, downtime and misbehavior, then `matureQueues` last; test.

83. **High — lengthening the unbonding period left existing queues under-collateralised, and changing the downtime window corrupted the tracking (finding 22, incomplete).** `src/app/core/staking.ts`. **Resolution:** fixed: adoption extends pending unbondings and redelegations by the difference and resets the signing records when the window changes; test.

84. **Medium — a valid parameter proposal could empty the active set.** `src/app/core/staking.ts`. **Resolution:** fixed: a proposal whose parameters would leave no active validator is dropped with a warning; test.

85. **High — a proposal's signals could exceed what its decoder accepts.** `src/app/core/evaluate.ts`, `src/app/core/types.ts`. **Resolution:** fixed: `MAX_SIGNALS = 1000` is enforced on signalling; test.

86. **Medium — accepted durations could overflow the timestamps derived from them.** `src/app/core/types.ts`. **Resolution:** fixed: `checkStakingParameters` bounds durations to a hundred years, amounts to the share supply and `minSelfBond` to at least one; test.

87. **Medium — queries saw a block half applied, and a verifier failure mid-block left the begin-block effects in place (finding 19, incomplete).** `src/app/core/app.ts`. **Resolution:** fixed: `finalizeBlock` runs inside an undo session that is committed just before the root, so the committed view that queries read is the previous block's until then, and a failure undoes the block and restores the pending state; test fails verification half way and compares with a clean execution.

88. **Low — inline and streamed genesis disagreed on a repeated `accounts` key, and a negative balance was silently dropped.** `src/app/core/genesis.ts`. **Resolution:** fixed: the last key wins in both parsers; a negative balance is refused; tests.

### RPC, light client and CLI

89. **High — event streams had no backpressure.** `src/rpc/server.ts`. A client that stopped reading held every event since. **Resolution:** fixed: a stream with more than 1 MiB queued is ended; the client resumes with `Last-Event-ID`.

90. **High — commit waiters were unbounded, and a transaction seen before waited the full timeout.** `src/rpc/methods.ts`, `src/rpc/events.ts`. **Resolution:** fixed: at most 1000 waiters (then `-32004`), a 120 s cap on the wait, cancellation in `finally`, and a transaction that was seen before but is neither pending nor committed is refused at once; test.

91. **High — header JSON let bytes move between hash fields.** `src/rpc/json.ts`. Hash fields were decoded at any length, so a response could shift bytes from one field into its neighbour and keep the header hash, which let a result-tree path pass as a transaction proof. **Resolution:** fixed: every hash and the proposer address must be exactly 32 bytes; height, time, version and round are validated; test.

92. **Medium — the light client did not bind a served header to the height it asked for, and accepted an anchor from the future or exactly one trusting period old (finding 43, incomplete).** `src/light/client.ts`. **Resolution:** fixed; tests.

93. **Medium — the CLI's account proof was not bound to the name, index or height requested, and `verify-tx` printed the node's height (findings 23 and 24, incomplete).** `src/cli.ts`. **Resolution:** fixed: the proof's type, index position, key and height must be the ones asked for, or the output says the proof is not verified and the exit code is 1; `verify-tx` prints the proof's height.

94. **Medium — an empty key name skipped the keystore's passphrase check, and editing the passphrase echoed it.** `src/wallet/keystore.ts`, `src/cli.ts`. **Resolution:** fixed: empty names are refused and the first key is checked whenever one exists; nothing is echoed after the prompt; test.

95. **Medium — `--rpc` dropped the node directory, malformed amounts were accepted, balances used the core precision, the expiration ignored the chain's maximum, failures exited 0, and `join` overwrote a node's configuration.** `src/cli.ts`. **Resolution:** all fixed: a directory keeps its keystore under `--rpc`; amounts must match `\d+(\.\d+)?` with no more decimals than the asset has; each balance carries its asset's precision; expiration is a minute or half the chain's maximum, whichever is less; failed executions and proofs set exit code 1; `join` validates its arguments first and refuses an existing `config.json`.

96. **Low — replay sent 1001 blocks (finding 25, incomplete); parameters were coerced; listing cursors scanned from the start; `validator` read live indices (finding 19, incomplete); `block` was not costly; ids of any type were echoed.** `src/rpc/*`. **Resolution:** fixed: exactly 1000; numbers must be safe non-negative integers and booleans must be booleans; `accounts` seeks the name index from its cursor (`scanFrom`) and honours a zero limit; `validator` and `delegation` read the committed view; `block` is costly; an id must be a string, a number or null; tests.

97. **Medium — two keystore handles over one file lose each other's keys (finding 26, remaining); `verify-tx` cannot verify a transaction older than the saved anchor.** `src/wallet/keystore.ts`, `src/light/client.ts`. **Resolution:** fixed in the third pass: every keystore write takes a lock file and starts from the keys on disk, so two handles keep each other's keys; the light client verifies backwards along the header-hash chain, so `verify-tx` and `account` reach heights before the anchor; tests.

98. **Low — JSON-RPC notifications receive a response.** `src/rpc/server.ts`. A request without an id is answered with `id: null`; the specification says it should not be answered at all. **Resolution:** fixed in the third pass: a request without an id is carried out and not answered (204 for a lone notification or a batch of them; a mixed batch answers only the requests that carry ids); test.

## Third pass: the items left as noted

The findings the second review left as noted, and the one regression test it had rebuilt without
checking that it fails without its fix, were taken up once more. Everything below is in the working
tree; the suite is 19 files and 132 tests, passing in 74 s, and the typecheck is clean.

- **Finding 68, evidence from before a state-sync join.** A node that joined from a snapshot held nothing
  below its join height, so a block carrying evidence of a double sign at an earlier height was refused as
  naming an unknown height (and the honest peers that served it were banned), while the executor, had the
  block got through, would have dropped the evidence from the application's misbehavior list and diverged.
  Now state sync fetches the headers of the evidence window before it installs: `headersRequest` serves up
  to a thousand headers downward from a height, each is bound to the one above by its hash, the validator
  sets they name are fetched by hash, and they are stored as header records below the lowest block, where
  `validatorSetAtHeight` and `blockTimeAt` read them, block sync checks evidence age through the executor,
  backfilled blocks replace them, and pruning lets them go once older than the window. Evidence the
  executor still cannot place halts the node with a reason instead of being left out. Two tests: a joiner
  without block backfill applies a block carrying evidence for a height below its join and a light client
  anchored after the join verifies a proof from before it; a joiner with a short window keeps only the
  headers inside it and prunes them as the chain moves on.
- **Finding 72, the interrupted install.** One transaction across the application and chain stores
  (`KvEnv.transaction`); the LMDB behaviour was probed first: nested store writes inside a root transaction
  land together, and a throw aborts them all. Header records written before the install are reused by a
  retry when they still chain.
- **Finding 78, shallow freezing and shared buffers.** Records are frozen through every nested object and
  array; sparse-tree roots, lookups and proofs are copies. The cost was measured before deciding.
- **Finding 97, keystore writers and old transactions.** A lock file and a re-read before every keystore
  write; backward verification in the light client, with a cache of the headers passed and a bound on the
  walk (`maxBackwardSteps`, 100,000 by default).
- **Finding 98, notifications.** Carried out, never answered.
- **Finding 99, the finding-37 test.** Found not to guard its finding; rebuilt and checked both ways.
