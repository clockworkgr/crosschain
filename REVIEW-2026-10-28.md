# Review of 2026-10-28

A full-codebase review run with the Codex CLI (gpt-6.1-sol, read-only, xhigh reasoning) after the
proofs, RPC and sync round. The findings as reported, each followed by what was done.

Regression tests live in `test/review.test.ts` (first review) and `test/review2.test.ts` (second review).

1. **Critical — Duplicate validators let one trusted key forge light-client trust.** [src/types/validator.ts:240](src/types/validator.ts:240), [src/light/client.ts:126](src/light/client.ts:126). Binary decoding accepts duplicate keys, and skipping verification counts their trusted power repeatedly. **Scenario:** one of four equal-power validators supplies a fabricated future set containing its key twice and signs a fabricated header; both quorum and overlap checks pass. Reproduced. P2p state sync uses this decoder; the tests cover only legitimate sets.

   **Resolution:** fixed: decoded sets are checked for duplicates, order, positive power and proposer index (`ValidatorSet.decode`); test

2. **Critical — The signature cache accepts corrupted signatures and splits application state.** [src/app/core/app.ts:446](src/app/core/app.ts:446). Cache hits depend on transaction body and signing address, without checking the supplied signature bytes. **Scenario:** prime some nodes with valid transaction T, then include T with a zeroed signature in a block → primed nodes execute it, cold nodes reject it, and their roots differ. Reproduced. The existing forged-signature test corrupts before priming the cache.

   **Resolution:** fixed: the cache binds the hash of the signature bytes; test

3. **Critical — Signature preverification makes ordinary authority updates depend on mempool history.** [src/app/core/app.ts:197](src/app/core/app.ts:197). All keys are resolved before any transaction executes, while cache hits bypass that resolution. **Scenario:** T1 installs a new active key and T2 spends using it; a node that checked both pending transactions executes both, while a cold node rejects T2 against the old authority. Reproduced with different roots for identical valid block bytes.

   **Resolution:** fixed: keys are resolved per transaction as the block executes, and checkTx waits behind a block in progress; test

4. **High — Re-proposing a locked block under another proposer can permanently halt consensus.** [src/consensus/consensus.ts:345](src/consensus/consensus.ts:345). Re-proposals retain the original block’s proposer address, but admission requires the current round’s proposer address. **Scenario:** obtain a polka, time out without a commit, and lose the original proposer → the next honest proposer’s re-proposal is rejected, including locally. Reproduced with three connected honest validators stuck at height 1.

   **Resolution:** fixed: a proposal is accepted from the round's proposer whatever proposer address the (re-proposed) block carries

5. **High — Restarting at an unfinished height can deadlock behind the signing guard.** [src/consensus/consensus.ts:285](src/consensus/consensus.ts:285). Consensus restarts at round zero, creates different proposal bytes, and schedules no proposal timeout when signing is refused. **Scenario:** persist a proposal, crash before committing, and restart a single-validator chain → the new timestamp conflicts with the stored proposal and consensus remains in `propose` indefinitely. Reproduced; the recovery test restarts one validator while others advance.

   **Resolution:** fixed: after a restart consensus resumes in the round after the one the guard already signed in; test

6. **High — An ordinary peer can force billions of synchronous proposer iterations before authentication.** [src/consensus/consensus.ts:344](src/consensus/consensus.ts:344). `proposerAt(p.round)` runs before proposal signature verification, and its cost is linear in the supplied round. **Scenario:** send a proposal for the current height with `round = 4294967295` and `polRound = -1` → the main thread performs billions of BigInt iterations before examining the signature.

   **Resolution:** fixed: proposals and votes more than 1000 rounds ahead are ignored

7. **High — Valid staking amounts can overflow serialized shares and halt finalized-block execution.** [src/app/core/staking.ts:102](src/app/core/staking.ts:102), [src/app/core/types.ts:363](src/app/core/types.ts:363). Shares are multiplied by \(10^6\), but remain serialized as u64 without admission bounds. **Scenario:** delegate `20000000000000` base units at the initial exchange rate → `checkTx` succeeds, then `root()` throws `u64 out of range` after the block has been decided. Reproduced.

   **Resolution:** fixed: share scale 10^3 and overflow guards in bond and reward; test

8. **High — State sync trusts unauthenticated proposer priorities.** [src/sync/statesync.ts:185](src/sync/statesync.ts:185). Imported sets are checked only by a hash that deliberately excludes priorities and the proposer index. **Scenario:** a snapshot peer supplies genuine keys and powers with altered priorities → the joining validator accepts them and derives different future proposers, rejecting legitimate proposals or proposing out of turn. Enough affected joining voting power can halt the chain.

   **Resolution:** mitigated: the sets for H and H+1 must pick the proposers the chain actually used at their commit rounds; the residual is documented

9. **High — Key rotation lets validators escape or misattribute later evidence.** [src/app/core/evaluate.ts:199](src/app/core/evaluate.ts:199), [src/app/core/staking.ts:390](src/app/core/staking.ts:390). Rotation removes the old address mapping, while punishment resolves historical evidence through the current mapping. **Scenario:** double-sign with key A, rotate to B, then receive valid evidence for A → no validator is found and punishment is skipped. Reproduced. Reusing A for another validator instead redirects punishment there.

   **Resolution:** fixed: every consensus key a validator ever used is recorded (type 13) and resolves evidence; keys are never reusable; test

10. **High — Queue slashing overlooks stake that still supplies voting power during the H+2 delay.** [src/app/core/staking.ts:345](src/app/core/staking.ts:345). Entries created at or before the infraction height are excluded. **Scenario:** undelegate substantial stake at H, double-sign at H+1 while that stake still contributes to the signing set, and receive evidence at H+2 → the unbonding entry is exempt because its creation height precedes the infraction.

   **Resolution:** fixed: entries from the height before the infraction are slashed too; test

11. **High — Redelegate followed by undelegate bypasses source-validator slashing.** [src/app/core/staking.ts:355](src/app/core/staking.ts:355). Redelegation punishment only takes funds from a current destination delegation. **Scenario:** after an infraction, redelegate A→B, then fully undelegate from B before A’s evidence arrives → the destination delegation is absent, so the slash is skipped and B’s unbonding entry remains intact. Reproduced: all 1,000 tokens survived the source slash.

   **Resolution:** accepted: same gap as Cosmos; documented

12. **High — Swapping authenticated keys within one block can prevent every affected node from restarting.** [src/db/database.ts:606](src/db/database.ts:606). History rebuilding interleaves deletion and insertion per object, so a later deletion can erase another object’s newly inserted key. **Scenario:** rotate validator keys A→temporary, B→A, temporary→B in one block → restart throws “rebuilt index does not match the live one.” Reproduced at the database layer. Tests cover undoing swaps, but not rebuilding their history.

   **Resolution:** fixed: a version's drops precede its puts in the rebuild; test

13. **High — Aborting an HTTP request body can terminate the node.** [src/rpc/server.ts:80](src/rpc/server.ts:80), [src/rpc/server.ts:148](src/rpc/server.ts:148). Body-read errors escape `handle()`, whose promise is discarded by the server callback. **Scenario:** begin a POST and disconnect during body upload → an unhandled rejection reaches Node’s default process-termination behavior. Confirmed that body-iterator errors escape the handler.

   **Resolution:** fixed: request errors are caught and the request destroyed; test

14. **High — Fetch responses allow unbounded socket buffering without scoring the requester.** [src/node/node.ts:259](src/node/node.ts:259), [src/p2p/tcp.ts:60](src/p2p/tcp.ts:60). Repeated requested hashes are served individually, and `socket.write()` backpressure is ignored. **Scenario:** repeatedly request 10,000 copies of a known pending transaction while barely reading responses → queued response buffers grow until memory exhaustion; these valid messages incur no misbehavior points.

   **Resolution:** fixed: fetches are deduplicated and capped at 256, oversize scored; a peer with 32 MB unread is dropped

15. **High — Block construction can repeatedly propose blocks exceeding its own size limit.** [src/consensus/consensus.ts:303](src/consensus/consensus.ts:303). The fixed 64 KiB reservation does not account for actual commit and evidence sizes. **Scenario:** fill the transaction budget and supply 100 valid pending evidence records → every honest proposer constructs an oversized block that validation rejects. No trimming occurs, and absent commits the mempool is never rebuilt to remove expired transactions.

   **Resolution:** fixed: the block is measured without transactions and the remainder given to them; evidence capped at 16 per block

16. **High — The signing guard’s rename lacks a directory durability barrier.** [src/store/files.ts:13](src/store/files.ts:13). The temporary file is fsynced, but the parent directory is not synced after replacement. **Scenario:** on a filesystem that loses an unflushed rename after power loss, a broadcast signature survives externally while the guard reverts to its older record, permitting a conflicting signature after restart. The missing barrier is confirmed; actual power-loss behavior was not reproduced.

   **Resolution:** fixed: the directory is fsynced after the rename

17. **Medium — Snapshot-height blocks and backfilled blocks are stored without authenticating their bodies or commit signatures.** [src/sync/statesync.ts:179](src/sync/statesync.ts:179), [src/sync/blocksync.ts:278](src/sync/blocksync.ts:278). Header-hash checks do not establish that supplied transactions, evidence, or commits match that header. **Scenario:** preserve a genuine header but replace its transactions and commit → fabricated content is persisted and indexed. Reproduced through backfill; subsequent inclusion proofs correctly fail.

   **Resolution:** fixed: snapshot-height and backfilled blocks are checked body against header and commit against the signing set

18. **Medium — Repeated raw transactions overwrite successful locations and break result proofs.** [src/store/blockstore.ts:90](src/store/blockstore.ts:90), [src/node/node.ts:362](src/node/node.ts:362). One global location per hash cannot reconstruct per-position execution results. **Scenario:** include `[T, T]` → execution results are success then duplicate failure, but the index retains only the failure and `queryTx` reconstructs two failures. Reproduced: RPC reports failure and its result proof fails verification.

   **Resolution:** fixed: results are stored per block and the first position of a repeated transaction owns its index entry; test (the position has changed since: see the fifth pass)

19. **Medium — RPC queries expose speculative state and label current values with historical heights.** [src/rpc/methods.ts:181](src/rpc/methods.ts:181). Several methods use live indices and objects, while their requested height affects only the proof or response label. **Scenario:** admit an uncommitted transfer, then request `account` at committed height H → balances include the pending transfer while the response and name proof refer to H. Validator, delegation, key, and account-list queries have related live-view inconsistencies.

   **Resolution:** fixed for account, validator and delegation; accounts list still scans live names

20. **Medium — A valid chunk for the wrong request can abort state sync instead of being retried.** [src/sync/statesync.ts:153](src/sync/statesync.ts:153). Chunk verification checks membership in the manifest but does not bind the embedded chunk to the requested job. **Scenario:** answer a request for chunk 0 with matching outer response fields but valid embedded chunk 1 → it is counted as completed, later imported twice, and the missing chunk causes a fatal root mismatch despite honest sources being available.

   **Resolution:** fixed: a chunk must match the request it answers

21. **Medium — Precommits arriving during application execution are lost from the fuller stored commit.** [src/consensus/consensus.ts:428](src/consensus/consensus.ts:428), [src/node/executor.ts:102](src/node/executor.ts:102). Updating the commit is discarded until executor state advances, and the accumulated vote set is not flushed afterward. **Scenario:** the fourth precommit arrives while asynchronous finalization is running → it is accepted but never stored, so the next block can penalize that signer as absent. The fuller-commit test delivers its vote after execution finishes.

   **Resolution:** fixed: the commit is stored again after the block is applied

22. **Medium — Unbonding changes are not coupled to evidence and light-client trust limits.** [src/app/core/staking.ts:410](src/app/core/staking.ts:410), [src/light/client.ts:76](src/light/client.ts:76). Governance replaces application parameters while engine evidence age and the default four-day trusting period remain independent. **Scenario:** adopt one-day unbonding → withdrawn validators’ old keys remain trusted for four days, and seven-day evidence can arrive after their funds have already been released.

   **Resolution:** fixed: the engine's evidence age follows the unbonding period after every commit; the light client's trusting period remains the client's choice

23. **Medium — The account CLI’s “verified” name proof has no trusted-chain anchor.** [src/cli.ts:299](src/cli.ts:299). It verifies against an app hash supplied by the same RPC server without checking that header’s commit or the light-client anchor. **Scenario:** a malicious RPC supplies a fabricated account tree, matching proof, and fabricated header → the CLI prints “name proof verified” for invented chain state.

   **Resolution:** fixed: the CLI verifies name proofs through the light client against its own anchor

24. **Medium — Transaction verification does not bind the proof to the requested transaction hash.** [src/cli.ts:346](src/cli.ts:346). The returned proof is verified independently of the CLI’s `hash` argument. **Scenario:** request verification of nonexistent or failed transaction X, and have the RPC substitute a genuine successful transaction Y with valid proofs → the CLI prints a successful verification for the request.

   **Resolution:** fixed: the CLI checks the returned proof is for the hash it asked about

25. **Medium — SSE replay performs unbounded synchronous work and buffering.** [src/rpc/server.ts:230](src/rpc/server.ts:230). Replay scans every retained height without a replay limit, rate charge, yielding, or write-backpressure handling. **Scenario:** open streams with `Last-Event-ID: 0` against a long archive and read slowly → repeated full-history serialization blocks consensus and queues large response buffers.

   **Resolution:** fixed: replay is capped at 1000 blocks, charged against the rate budget (a stream asking for a replay it cannot afford is refused with 429 instead of opening with a gap), and stops on backpressure

26. **Medium — Keystore updates can destroy all previously stored keys on interruption.** [src/wallet/keystore.ts:110](src/wallet/keystore.ts:110). Every save directly truncates and rewrites the only keystore file. **Scenario:** interrupt an `add` or `remove` during the write → the JSON may be empty or partial, making every previously encrypted seed unavailable, not just the key being changed.

   **Resolution:** fixed: the keystore is written temp-fsync-rename

27. **Medium — The core asset can be issued outside the staking mint.** [src/app/core/evaluate.ts:159](src/app/core/evaluate.ts:159). `assetIssue` treats the core asset as an ordinary issuer-controlled asset. **Scenario:** the genesis core issuer issues more core tokens while inflation is zero → supply increases through a transaction, contradicting STAKING.md’s mint-only supply invariant and allowing additional stake creation up to max supply.

   **Resolution:** fixed: the core asset cannot be issued; test

28. **Low — Failed transactions can leave successful-looking virtual history entries.** [src/app/core/history.ts:127](src/app/core/history.ts:127). Virtual entries bypass the transaction’s discardable history buffer. **Scenario:** execute `unjail` followed by an operation that fails in the same transaction → database rollback restores the jailed status, but commit persists and streams the virtual `unjail` entry.

   **Resolution:** fixed: virtual entries inside a transaction follow its outcome; test

29. **Low — Zero-version retention retains every sparse-tree version internally.** [src/db/smt.ts:130](src/db/smt.ts:130). Pruning runs only when retention is positive. **Scenario:** configure `retainVersions: 0` to keep only current proofs → every block still retains another root pointer, and changed historical paths remain reachable indefinitely, causing unbounded memory growth.

   **Resolution:** fixed: pruning runs at any retention; test

Strongest parts: strict binary decoding, signature domain separation, and domain-separated Merkle hashing.  
The basic H+2 set pipeline and deferred state/result commitments are clear and consistently implemented.  
Object, sparse-key, and range proofs have substantial tamper, historical-version, and reconstruction coverage.

## Found while confirming the suite after the fixes

30. **High — block sync recursed between `check()` and `drain()`.** `src/sync/blocksync.ts`. After the stage-3 rewrite, `drain()` re-ran `check()` unconditionally and `check()` ran `drain()` again. With nothing in the buffer the drain never reached an `await`, so every peer status message during a sync recursed synchronously until the stack overflowed. The overflow surfaced as a swallowed rejection (`Exception in PromiseRejectCallback`), so the sync tests still passed.
   **Resolution:** fixed: `drain()` re-checks only after a block left the buffer; test counts the state reads of one unanswerable status (7492 before, a handful after).

31. **Medium — an event stream asking for a replay it could not afford opened with a gap.** `src/rpc/server.ts`. Charging the replay (finding 25) made an unaffordable replay silently skip, so the client saw a live stream and believed itself caught up. The rpc test then spun forever on a finished stream: awaiting an already-finished reader never yields to timers, so the test timeout could not fire and the suite hung.
   **Resolution:** fixed: the rate check runs before the headers and refuses with 429; the test reads with a guard against ended streams and asserts the 429.

## Found by the benchmarks

32. **High — a block not seen through the mempool was verified one signature at a time.** `src/app/core/app.ts`. The fix for finding 1 resolved keys per transaction as the block executes, which also moved verification into that loop, so the worker pool received one job at a time: a cold block ran at single-thread speed (930 transfers/s) and block sync with it. The two concerns are separable: a cache entry records that a signer signed a body, which no state change can invalidate, so all of a block's uncached signatures can be verified in one batch first, with the per-transaction pass still resolving each signer against the state its transaction applies to.
   **Resolution:** fixed: `prewarmSignatures` batches the block before the loop (5,100 transfers/s cold on 11 threads; the warm path is unchanged). Existing tests cover warm and cold agreement.

33. **Medium — a request sent the instant a peer connected could be dropped by the other side.** `src/p2p/network.ts`. The dialing side is established as soon as it sends `auth`; the accepting side still awaits the verification of that signature, during which its connection had no frame handler. Block sync asks for blocks from the first peer it sees, so a joining node's first request vanished and it waited out a five-second timeout before retrying elsewhere.
   **Resolution:** fixed: frames received during a handshake step are held (at most 64) and delivered once the peer is established; a test with a slow verifier sends on `onPeer` and sees the message arrive.

34. **Low — the worker verifier let the process exit while a caller awaited it.** `src/crypto/verifier.ts`. Workers were unreferenced for life, so a process whose only pending work was a verification (a CLI, a benchmark) exited with an unsettled promise.
   **Resolution:** fixed: a worker is referenced while it has jobs in flight and unreferenced when idle.
35. **High — a genesis over 512 MB could not be loaded at all.** `src/types/genesis.ts`, `src/app/core/genesis.ts`. The application state was embedded as one string inside `genesis.json` and parsed with `JSON.parse`; V8 refuses strings over 512 MB, and a document that fits still needed several times its size in heap. A genesis of a few hundred thousand accounts (two 1312-byte keys each) is well over that.
   **Resolution:** fixed: `genesis.json` may name an `appStateFile`; the application reads it as a token stream with `stream-json`, assembling one account at a time, so memory holds the objects and never the text; the node does this once, when its store is empty. The genesis benchmark loads a gigabyte this way.

36. **Medium — the encoded bytes of every object changed by a version were kept until the next root.** `src/db/database.ts`, `src/app/core/app.ts`. The change list a store writes was retained by the database afterwards: after genesis a second copy of the whole state, and after a restart (where the root is recomputed over every object to check the stored app hash) the same again, for nothing. The genesis benchmark showed it as 500 MiB per gigabyte of genesis.
   **Resolution:** fixed: the application drops the list once persisted, and the reopen path drops it once the root is checked; a test asserts both.


## Found while documenting

Writing the part-by-part tutorial (docs/tutorial/) meant reading every file against the design
record and the specifications. These are what that reading turned up, with what was done.

37. **High — a block re-proposed with a proof of lock was checked for clock drift against the current time.** `src/consensus/consensus.ts`. Every proposal went through the timeliness check, including a re-proposal of a block that already had a polka, whose time was set by its first proposer. A round that stalled longer than the drift limit (15 s by default) could then never decide that block: the locked validators prevote nil for it, no other block can gather a polka against their locks, and the height stalls for good. CometBFT applies timeliness only to fresh proposals (`polRound == -1`).
   **Resolution:** fixed: the drift check applies to fresh proposals alone; a network test stalls round 0 of two heights with a lost proposal and a lost precommit under a 300 ms drift limit and sees the re-proposal decide.

38. **Low — a transaction refused as full after its check was remembered as seen.** `src/mempool.ts`. The seen cache was written before the check (so a concurrent duplicate is checked once); when the pool filled during the check the transaction was refused but stayed cached, and a resubmission heard `seen` until the cache rolled over.
   **Resolution:** fixed: the late refusal forgets the hash; test.

39. **Medium — a decided height was written to the block store in four transactions.** `src/node/executor.ts`, `src/store/blockstore.ts`. DESIGN.md section 4 says block, commit and state land in one transaction; the code wrote the block, the next set, the set by height and the state separately. A crash between them left a block and its transaction index entries without the state that goes with them; a different block decided for that height on restart would overwrite the block but not every index entry.
   **Resolution:** fixed: the block store has `batch()`, and the executor saves a height inside one; test counts the store's transactions.

40. **Medium — a failed verification worker took the whole pool with it, and `close()` left callers waiting.** `src/crypto/verifier.ts`. A worker error rejected every pending job of every worker and the dead worker stayed in the rotation, so later jobs sent to it never completed; `close()` terminated workers without settling what they still held.
   **Resolution:** fixed: a failed worker rejects only its own jobs and is replaced; `close()` rejects what is pending; test.

41. **Low — a string beginning with a byte-order mark did not decode to what was encoded.** `src/codec/reader.ts`. `TextDecoder` strips a leading U+FEFF by default, so the codec was not a bijection on such strings.
   **Resolution:** fixed: the decoder keeps the mark; test.

42. **Low — a virtual history entry raised inside a transaction always named operation 0.** `src/app/core/history.ts`. An unjail in the third operation of a transaction was recorded against the first.
   **Resolution:** fixed: the recorder is told which operation is running.

43. **Medium — the light client accepted an anchor older than the trusting period.** `src/light/client.ts`. `trust()` checked the hash and the commit but not the age, so a stale anchor was accepted until the first verification step; a set that had since unbonded could have signed it.
   **Resolution:** fixed: an anchor outside the trusting period is refused; test.

44. **Medium — after a restart, a past-height proof for an object type that nothing changed in the window threw.** `src/db/database.ts`, `src/db/merkle.ts`. Reloading history lowered a tree's version floor only when the record named that tree; a type untouched in every retained version kept its floor at the restart height, so `proofAt` for it at any earlier height was refused although `lowestVersion` admitted the height. Accounts on a quiet chain are exactly such a type.
   **Resolution:** fixed: loading a record lowers every tree's floor, since a tree the record does not name was unchanged and its later state is also its state then; test reopens a store and proves an account and a balance at a past height.

45. **Low — one chunk timeout marked a snapshot source bad for the whole join.** `src/sync/statesync.ts`. A transient timeout counted like a corrupt chunk; with two sources, one slow reply aborted the join.
   **Resolution:** fixed: a source is dropped after three failures; a bad chunk still costs it at once.

46. **Low — backfill never asked a peer again once it had declined one old block.** `src/sync/blocksync.ts`. A peer that was itself still syncing was written off for good.
   **Resolution:** fixed: when every peer has declined, the list is cleared after thirty seconds and backfill tries again.

47. **Low — smaller fixes.** IPv6 addresses in brackets were accepted by the peer database but not parsed by the TCP transport (`src/p2p/tcp.ts`); the in-memory transport's `close()` removed the listener under its own address instead of the bound one (`src/p2p/memory.ts`); an event stream accepted unknown event types silently and rate-limit buckets were never evicted (`src/rpc/server.ts`); a newly connected peer was not told about pending evidence, which RPC-SYNC-PROOFS.md section 4.4 promises (`src/node/node.ts`); the `tx` command asked for a proof it did not use and `keys list` created a keystore when none existed (`src/cli.ts`); the toy application's snapshot was not written atomically (`src/app/kvstore.ts`); the fallback propose timeout ignored the round's delta (`src/consensus/consensus.ts`). All fixed.

48. **Dead code and names.** `Consensus.onDecision` and its listener list had no caller; `validate.ts` re-exported `blockHash` for nobody; the evidence pool's `evidenceHash` shared its name with the header's `evidenceHash` in `types/block.ts` while hashing something else. Removed, removed, renamed to `evidenceId`. A staking test compared the community pool with itself (`pool >= pool + T(10) - T(10)`); it now asserts the exact movement.

49. **Specifications brought back in line with the code.** STAKING.md: the redelegation and signing-info fields, `inflationPpb` for `inflationBps`, `SHARE_SCALE = 1000`, the downtime set (`expectedSigners`) and the slashing window (`creationHeight >= height - 1`). RPC-SYNC-PROOFS.md: the history key prefixes and the slash entry, which calls are costly, the snapshot message names, the `snapshots` RPC stub, where the transaction-proof verifiers live, and what block sync does on a timeout and when it asks for a block. DESIGN.md: the peer database fields, scoring, the dynamic properties, where validators come from, authenticated indices in the type leg, and two simplifications added to section 10 (the lock is not kept across a restart; the node's default verifier is inline). Comments: `genesis.ts` (which amounts are whole tokens), `lmdb.ts` and `app.ts` (the CLI no longer reads the store), `keys.ts` and `index.ts` (the B+ tree file's name).

Noted and left as they are, each a judgement for later: the transaction index keeps one location per hash chain-wide, so a transaction that failed in one block and succeeded in a later one points at the later one, and pruning that later block removes the entry; a `txsRoot` proof binds the tree height but not the exact count; `Node` defaults to the inline verifier; the evidence pool's hash sets are pruned only by age; `loadSnapshot` does not check that every registered type has a section; `openDB` on a missing name in a read-only LMDB environment returns undefined; `Keystore.remove` has no command; the RPC's `key`, `account` and `delegation` answer from the live indices with a proof at the requested height (finding 19); `validator` and `balance` take no height; a JSON-RPC batch is charged one token; the ping carries no clock offset; several decode paths accept out-of-range numbers that consensus bounds later; the tests chapter lists the suite's weaker assertions.


## Second review (Codex, per module)

After the first round's fixes, the benchmarks and the tutorial, the codebase was reviewed again,
this time one module per reviewer (engine, network and sync, database and store, application,
RPC and CLI, documentation, tests), each told what the specifications and the tutorial claim and
asked to check the code against them. Reviewers reproduced findings with probes where they
could. What follows is each finding as reported and what was done; the module reviews' remarks
on the documentation were folded into the specifications and the tutorial (see the end).

### Engine

50. **High — a vote for the next height was verified against one set and counted with another.** `src/consensus/consensus.ts`. Votes arriving early for H+1 were checked against the set the node happened to hold for H+2 and then replayed into H+1's round, where their index named a different validator with different power. **Resolution:** fixed: early votes are verified against the set of their own height, buffered together with the public key that verified them, and replayed only if that key still holds the index when the height begins; test.

51. **High — later-round gossip left out the polka votes a re-proposal needs.** `src/consensus/consensus.ts`. Periodic gossip re-sent the current round's votes only; a validator that missed the prevotes of the valid round could never accept the re-proposal that cites it, and with one silent validator the height could stall for good. **Resolution:** fixed: gossip also re-sends the prevotes of `validRound`.

52. **High — a relay could poison a round by attaching another body to a genuine signed proposal.** `src/consensus/consensus.ts`. The proposal's signature covers the header; a body that did not match the header was rejected, but only after the round had recorded that a proposal arrived, so the genuine one was then ignored. Bad proposal signatures also went unscored. **Resolution:** fixed: a body that does not match its header is dropped without recording the round and the relay is scored 20; a bad signature scores 20 like a bad vote; `bodyMatchesHeader` moved to `validate.ts`.

53. **Medium — the periodic re-send of a re-proposal named the block's builder, not the round's proposer (finding 4, incomplete).** `src/consensus/consensus.ts`. The header keeps the address of whoever first proposed the block; a later round's proposer re-proposing it never re-sent it. **Resolution:** fixed: the re-send is keyed on `proposerAt(round)`.

### Network and sync

## Fourth pass: the judgement calls

The thirteen items of the paragraph "Noted and left as they are" above, which the first review set aside
as judgements for later, were taken up; the paragraph stays as the record of what was found. Everything
below is in the working tree; the suite is 25 files and 213 tests (212 passing and 1 skipped under
`CHAIN_SCHEME=secp256k1`), and it passes with `INDEX_TREES=0 TREES=0` as well (the figures of this
pass; the fifth pass below gives them as they stand). The new cases are in
`test/review4.test.ts`, nine of them, with assertions changed in `test/txproof.test.ts`, one added to
`test/store.test.ts`, one to `test/db.test.ts`, and the write count of the finding-39 case in `test/review.test.ts` taken after
the store is opened, since opening a new store now writes the layout of its transaction index once.

- **The transaction index kept one location per hash.** `src/store/blockstore.ts`. The key is now `'t'`,
  the hash and the height, one entry for every block a transaction is in. `txLocations(hash)` lists every
  block still held that carries the transaction, oldest first; `txLocation(hash)` is the block it
  succeeded in if there is one, else the newest. Pruning a block removes that block's entry only. A store
  of the old layout has its entries moved to the new keys once, when it is next opened
  (`migrateTxIndex`), 5,000 entries a write, with the marker `'T'` written last so that a move cut short
  is taken up again; a store that cannot be written is read in the old layout as it is. The RPC's `tx` adds `attempts`
  (height, index, ok and error of each) when there is more than one. (Since this pass the key has changed
  again: it is `'x'`, a segment of 32 blocks, the hash and the height, and `migrateTxIndex` moves either
  older layout into it. RPC-SYNC-PROOFS.md section 2.3 has the layout as it stands.)
- **A `txsRoot` proof bound the tree height but not the exact count.** `src/types/txproof.ts`. `TxProof`
  and `ResultProof` no longer state a count, in memory or on the wire: the root commits to the tree's
  height, which the path's length is, and not to how many transactions there are, so the count was a
  statement the proof did not prove. Verification requires the index to be one the path's length can
  address (`index < 2 ** siblings.length`), and at most 32 siblings are read. A leaf is hashed apart from
  an inner node, so a path of another length cannot lead to the same root. The proof encoding the RPC
  returns changed; nothing in consensus did.
- **`Node` defaulted to the inline verifier.** `src/node/node.ts`. A node given no `verifier` makes a
  `WorkerVerifier` and closes it in `stop()`. Several nodes in one process share one and pass it, as the
  tests' helper and the CLI do.
- **The evidence pool's hash sets were pruned only by age.** `src/consensus/evidence.ts`,
  `src/node/executor.ts`. Only a proposer pruned, and only what was pending, so the committed set and the
  inventory grew for ever and a node that never proposed pruned nothing. The committed set now holds the
  evidence, `pruneIf` removes stale evidence from pending and committed alike together with its inventory
  entry, `markCommitted` records the inventory entry of evidence that came in a block, and the executor
  prunes the pool by the evidence age after every commit, on every node. What waits is bounded as well
  (`EvidencePool.MAX_PENDING`, 1,000; more is refused, one piece being enough to punish a validator), and
  `held` reports the three sizes.
- **`loadSnapshot` did not check that every registered type has a section.** `src/db/database.ts`. One
  section per registered type is required, in the order `encodeSnapshot` writes them; a section missing,
  repeated or out of order is refused with a `DbError` before the root is compared, which used to be the
  only guard.
- **`openDB` on a missing name in a read-only LMDB environment returned undefined.** `src/store/lmdb.ts`.
  `store(name)` throws `the store has no database named X, and a read-only environment cannot create it`
  where the first read used to fail far from the cause.
- **`Keystore.remove` had no command.** `src/cli.ts`, `src/wallet/keystore.ts`. `keys remove <name>`
  prints `removed <name> <address>`; it needs the keystore to exist and the passphrase.
  `Keystore.remove` throws `no key named X` for a name that is not there, where it was silent. The
  command itself is tested: the keystore case of `test/review4.test.ts` runs `keys add`, `keys remove`
  and `keys list` in child processes and checks the exit codes, the line printed, the refusal of a name
  that is not there and that a path with no keystore gets none.
- **`key`, `account` and `delegation` answered from the live indices with a proof at the requested height
  (finding 19).** `src/rpc/methods.ts`. Every state query answers as of one height, `height` in the
  parameters or the last committed one, and returns it. A unique index is read at the height from its own
  sparse tree: the key proof is made with `proveKeyAt` and the id taken from the proof's leaf, so the
  value is what the proof proves, and the live index, which holds the writes of the block in progress, is
  not asked. `account` reads the account, its balances, its validator and its history count as of the
  height (`CoreApp.accountHistoryTotalAt`, `HistoryLog.totalAt`); `delegation` gives the tokens by the
  validator as of the height. A height outside what the application holds is refused with `-32001`,
  `the state at height H is not kept (heights A to B are)`, on `object` too, where it used to surface as
  an invalid-params error from the database. Two fields cannot be answered for a past height from today's
  indices alone: `validator`'s `delegators` (a delegation is removed when its last share
  goes) and `delegation`'s `unbonding` (an entry is removed when it matures). They were `null` at a past
  height at first and are now answered for any height the node holds: `ObjectDatabase.changedSince`
  (`src/db/database.ts`) gives every object of a type that a later version created, changed or removed,
  from the window in memory and, below it, from the store's history records, and `listAt` in
  `src/rpc/methods.ts` reads those and the ones the index gives now as of the height and keeps what
  existed then. The CLI's `account`
  command, which asks one height back with the proof, now gets the balances and the history count of
  that same height.
- **`validator` and `balance` took no height.** `src/rpc/methods.ts`. Both take `height` and return it,
  and both are costly methods now. `balance` for an account named that did not exist at the height is
  `-32001`; by id it is 0.
- **A JSON-RPC batch was charged one token.** `src/rpc/server.ts`. The HTTP request pays one token as
  before, which covers its first call; each further call of a batch pays one more, before its method is
  looked up, and a call that cannot pay is answered `-32004` in its place in the batch. A batch of 20
  cost one token before.
- **The ping carried no clock offset.** `src/p2p/messages.ts`, `src/p2p/network.ts`. `pong` is
  `{ time, now }`, the ping's time echoed and the answerer's clock, 16 bytes of payload where it was 8.
  `Peer.clockOffsetMs`, null before the first pong, is the peer's clock when it answered plus half the
  round trip less this node's clock on receipt. A pong whose round trip is negative or longer than the
  idle timeout is ignored; a peer is logged when a pong first shows it 2 s or more off (`CLOCK_WARN_MS`), and again when its offset reaches that after a pong that showed less; the RPC's
  `peers` returns the offset; `NetworkConfig.clock` gives a test's network another clock. The offset is
  what the peer claims, good for noticing a wrong clock and nothing more.
- **Several decode paths accepted out-of-range numbers that consensus bounds later.** `src/codec/reader.ts`.
  `u53()` and `i53()` read a u64 or i64 that is used as a JavaScript number and throw a `CodecError`
  (`number out of range`) beyond `Number.MAX_SAFE_INTEGER`, where `Number(r.u64())` rounded and two
  encodings decoded to one value. They are used for a proposal's `polRound`, a validator set's proposer
  index, a snapshot chunk's `from`, `to` and instance numbers, the database's snapshot counters and
  history records, and the counters and versions `src/app/core/app.ts` reads from its store.
- **The tests chapter lists the suite's weaker assertions.** Nothing to do: `docs/tutorial/15-tests.md`
  was rewritten after the review and holds no such list any more.

### Network, sync, consensus and mempool

- **An outbound connection counted two successes.** `src/p2p/network.ts`. `markSuccess` is called in
  `connect` alone, once per dial.
- **A connection sent a `reject` frame was closed before the frame could leave.** `src/p2p/network.ts`.
  A connection the node rejected (kept in `rejected`) is closed by the 50 ms timer and, while the
  network runs, by nothing sooner; a handshake that fails otherwise is closed at once. A stop closes
  it without waiting for the timer (the item "A refused connection and its timer outlived a stop"
  below).
- **A ban and the connect loop's exclusion used the resolved socket address.** `src/p2p/network.ts`.
  `Peer.dialedAddr` (null for an inbound peer) is the address as it was dialed; `score` bans it and
  `connectLoop` excludes it, so a ban lands on the record the peer database holds. An inbound peer is
  banned by id only.
- **An `addrResponse` nobody asked for was taken.** `src/p2p/network.ts`. One response is taken for each
  `addrRequest` sent to that peer (`addrAsked`); any other is ignored, without a score.
- **`peers.json` was written in place and parsed unguarded.** `src/p2p/peerdb.ts`. `save` writes
  `peers.json.tmp` and renames it; a file that cannot be read or is not a list is taken as empty, and the
  node starts from its seeds.
- **Block sync applied after a stop, kept stale blocks and trusted the shape of a response.**
  `src/sync/blocksync.ts`. A stopped sync applies nothing after a verification returns (and sets no
  timer after an application returns: the item "Block sync set its timer again after a stop"
  below); the buffer is
  dropped when no peer is ahead; a `blocksResponse` must hold at most `count` blocks, each at height
  `from + i` with a commit naming its hash, or none of it is buffered, the peer is charged 50 points
  (`blocks response does not match the request`) and its height forgotten.
- **State sync threw on a snapshot below the trust height and passed over an undecodable manifest
  without a charge.** `src/sync/statesync.ts`. Only snapshots with `height + 1 >= trustHeight` are
  candidates; when none qualifies a warning is logged and the node replays from genesis, as when none is
  offered. A manifest that does not decode costs the peer 50 points and the next source is asked.
- **A vote far ahead was verified before it was dropped, and block requests outlived their height.**
  `src/consensus/consensus.ts`. `handleVote` drops a vote more than `MAX_ROUND_AHEAD` rounds ahead before
  verifying its signature, and `fetchRequested` is cleared at the start of every height.
- **An empty validator set decoded with any proposer index.** `src/types/validator.ts`. It decodes only
  with -1, else `validator set proposer index out of range`.
- **The seen cache could forget a pooled transaction, and two concurrent checks could both take the last
  place.** `src/mempool.ts`. The cache maps each hash to its place in the ring and eviction removes a
  hash only if the place overwritten is still its own; `seen()` and the duplicate check of `addTx` ask
  the pool as well, so a pooled transaction is never checked or announced again. `admit` reserves a
  place (`txs.size + reserved < limit`), released on every way out; a transaction `admit` refused is
  answered `full` or `paused` and forgotten.
- **Peers could fill the buffer of next-height proposals with unverified ones.**
  `src/consensus/consensus.ts`. `holdNextHeightProposal` holds a proposal for the next height only if
  it is fresh (`polRound` -1), its round is no more than `MAX_ROUND_AHEAD`, its block is of the
  proposal's height and its signature verifies with the key of the validator, in the next height's
  set, that the block names as proposer. Of the 8 held (`MAX_NEXT_HEIGHT_PROPOSALS`) one validator
  takes 2 (`MAX_NEXT_HEIGHT_PROPOSALS_PER_VALIDATOR`) and one for a round; a proposal there is no
  place for is dropped before its signature is verified, and a bad signature costs the sender 20
  points. The check is on the proposal's signer, not on the peer that relays it: any peer may relay a
  proposal a validator signed, nothing takes a place without the signature of a validator of the next
  height's set, and the limits are counted by signer.
- **A vote for the next height was verified and held each time it came.** `src/consensus/consensus.ts`.
  `handleVote` drops one that is already held, the same round, type, validator index and block hash
  (`nextHeightVoteKey`, `nextHeightVoteKeys`), before its signature is verified, so a peer repeating a
  valid vote costs no verification and cannot fill the 4,096 places with copies. A conflicting vote,
  with another block hash, is still verified and held.
- **The mempool hashed a transaction before it checked its size.** `src/mempool.ts`. `addTx` checks the
  size first; the `too-large` answer works its `hash` out only if it is read.
- **A proposal nobody waited for could end the process at a stop.** `src/consensus/consensus.ts`.
  A validator's own proposal (`propose`) and the proposals held for a height (`startHeight`) were
  handed to `handleProposal` with `void`. The node's handlers for a peer's messages had been given
  an end (`detached`, the item "Work that outlived a stop could reach a closed store" below); these
  two calls are inside consensus and had none. A node that made its own verifier pool closes it as
  it stops, a verification that is out then rejects with `verifier closed`, and for a proposal of
  either kind that was a rejection nobody handled, which ends a Node process. Both calls now go
  through `proposalUnawaited`, which catches whatever `handleProposal` ends with and logs `handling
  a proposal failed` with the height and round, at `debug` once consensus is stopped and at `error`
  while it runs. The test `catches the failure of a proposal nobody waits for` makes
  `handleProposal` reject and calls it that way.
- **A dial in progress at a stop went on to connect.** `src/p2p/network.ts`, `src/p2p/tcp.ts`.
  `Network.connect` looked at `running` before the dial and not after it, so a dial that resolved
  once the network was stopped was sent a `hello` and its handshake begun; and `TcpTransport.close()`
  closed the listener alone, so a socket still connecting connected later or waited for the
  operating system to give up. `connect` now reads `running` again when the dial resolves and
  throws `network stopped`, and the connection is closed with nothing sent on it. `TcpTransport`
  keeps the sockets still connecting in `dialing`, and `close()` destroys each and rejects its dial
  with `transport closed`. The tests `sends nothing on a connection that opened after it was
  stopped, and leaves no refused connection or timer behind` (its first half) and `ends a dial that
  is still connecting when the transport is closed` cover the two.
- **A refused connection and its timer outlived a stop.** `src/p2p/network.ts`. A connection sent a
  `reject` frame is closed 50 ms later, and `rejected` was a `WeakSet` that could not be gone
  through: `stop()` closed neither the connection nor its timer, and a handshake whose check came
  back after the stop set a new one. `rejected` is now a `Map` of the connection to its timer. The
  timer removes its entry as it closes the connection, `stop()` clears the timers still there and
  closes their connections, and `reject()` on a stopped network closes the connection at once,
  sending nothing and setting no timer. The second half of the same test refuses a connection, stops
  the node inside the 50 ms and finds the map empty and the connection closed.
- **Block sync set its timer again after a stop.** `src/sync/blocksync.ts`. `drain` looked at
  `running` on entry and after a verification, and not after a block had been applied. A sync
  stopped while a block was being applied went round its loop once more: with another block held
  and consensus deciding it called `later(200)`, which set the grace timer that `stop()` had just
  cleared, and otherwise it began verifying the next block. `drain` now checks `running` at the top
  of every pass, and `later` sets no timer on a stopped sync. The test `sets no timer when it was
  stopped while a block was being applied` holds an application open, stops the sync with a block
  held and consensus deciding, and finds one block applied and no timer.
- **A handshake waited out its timeout on a connection that had already closed.**
  `src/p2p/network.ts`. A connection tells of its close once (`BaseConn.onClose`), to the callback
  registered when it closes. One that closed between two steps of its handshake, a `hello` followed
  in the same chunk by a frame above the size limit for one, had told the step that was over, and
  the next `nextMessage` registered a callback that was never called: it waited the whole handshake
  timeout, 10 seconds by default, holding a place among the pending inbound handshakes, on a timer
  that `stop()` could not clear, since closing a closed connection does nothing. `nextMessage` now
  rejects at once with `closed during handshake` when it is given a closed connection, and sets no
  timer. The test `does not wait on a connection that closed between two steps of its handshake,
  and leaves no timer of the wire behind` (its first half) closes the accepting side's connection
  as the `hello` is handed over, under a handshake timeout of 60 seconds, and finds no handshake
  pending within two.
- **The in-memory hub's timers outlived the networks on it.** `src/p2p/memory.ts`. The hub delays
  the acceptance of a dial, the delivery of a frame and the far side's view of a close by
  `latencyMs`, and each was a `setTimeout` nobody kept: closing a transport removed its listener
  and nothing else, so a stopped network was still handed a connection, frames and closes that
  were on their way, and the timers stayed with the process. Each transport now has an `End` that
  holds its connections and the timers of what is on its way to them. Closing the transport clears
  the timers and closes the connections, and a connection on its way to a listener that has closed
  is closed, not accepted. The tests and `scripts/localnet.ts` run on the hub; a node over TCP
  never had these timers. The second half of the same test starts two networks on a hub with a
  latency of five seconds, dials, stops both and counts as many active timers as before.

### Node, executor and block store

- **The data directory's lock was read and then written, keyed by the path as given and released
  first.** `src/node/node.ts`. The pid is written to a private file, `LOCK.<pid>.<8 hex>`, which is
  hard-linked to `LOCK` and then unlinked, so the claim appears with the pid already in it: one created
  empty and filled afterwards could be read as stale in between, and both processes would start. The
  link fails with `EEXIST` when a claim is there; then the pid is read, a live one refuses, and a stale
  one is taken over. A stale claim is removed only by a process that holds a
  second exclusively created file, `LOCK.takeover`, and only after it has read the claim again and
  found it still stale, so two processes that find the same stale `LOCK` at the same instant cannot
  each remove the other's new claim and both start. A process that finds `LOCK.takeover` present waits
  20 ms and tries again. The attempts are counted whichever way each ended, and the fifty-first, about
  a second later when that file is in the way, fails with `could not claim it in 50 attempts;
  <path>/LOCK.takeover may have been left by a process that stopped while taking over a stale claim:
  check that no node runs on the directory, then remove it`. Releasing removes `LOCK` only if it still
  holds this process's pid. The in-process table
  is keyed by the directory's real path. `stop()` releases the lock last, in a `finally`, after the
  network has stopped, the executor is idle and the store is closed (the next item). The verifier is
  closed before the release where the node made it; one the caller passed in the caller closes.
- **The claim was released before a store the caller had opened was closed.** `src/node/node.ts`,
  `src/store/lmdb.ts`, `src/cli.ts`. The CLI opened the LMDB environment and handed it to its node, and closed it
  after `stop()` had returned, so `LOCK` went while the store was still open. `stop()` now closes the
  store the node opened and also one it was handed for a directory it holds the claim on, before the
  release. `LmdbEnv.close()` closes once and returns that one close to every caller
  (`this.closing ??= this.root.close()`), so its owner closing it again is harmless and a second caller
  waits for the close instead of returning at once. `stop()` is the same: it returns the one shutdown
  to every caller (`this.stopping ??= this.shutDown(beforeClose)`, the body now in the private `shutDown()`), so
  two callers stopping at once wait for it, and the claim is released when it is done. The test
  `closes a store it was handed for a directory it claimed before giving the claim up` stops the node
  twice at once. An environment handed to a node without a data directory stays the caller's.
  Two changes followed. The CLI's `start` no longer opens the environment: it passes
  `dataDir` alone, and the node claims the directory and then opens the store, so a second `start` on
  a directory in use is refused before it has opened anything there. And `stop(beforeClose?)` takes a
  function the node waits for after it has stopped what it runs (consensus, block sync and the network
  stopped, the block being applied finished) and before it closes its store. Work of consensus or
  block sync that is suspended on a verification or a request at that moment is not ended by this;
  the item "Work that outlived a stop could reach a closed store" below says what becomes of it. The CLI's `shutdown`
  starts the RPC server's stop at once and passes its promise, so a request still being served reads
  a store that is still open, and the claim is released after the close as before. If the function
  rejects, the store is still closed and the claim released, and the error reaches the caller of
  `stop`; only the first caller's function is used. The test `waits for whoever still reads the store
  before closing it, and releases the claim after` covers both outcomes.
  `shutDown()` was then made to try every step whatever the ones before it did: stopping consensus,
  block sync and the network, waiting for the block being applied, the caller's function, closing the
  store and closing the node's own verifier pool each run in a `try` of their own, the claim is
  released last, and the first failure is the one `stop()` rejects with, whatever value it is. The
  same test gained a part for that: a function that rejects with `undefined` still makes `stop`
  reject, and the claim is gone. In `src/cli.ts`, `start` sets up its signal handlers and `shutdown`
  before `Node.create`. A signal that comes while the node is being made is acted on once it is made,
  and the node is stopped as usual; if the node has not been made five seconds after such a signal the process exits as it is, which leaves the claim of a process that is gone for the
  next start to take over. A failure of `node.start()` or of the RPC server's start, its address in
  use for one, is logged as `start failed` and the node is stopped like any other before the process
  exits with status 1, so the store is closed and the claim released. A failure while stopping is
  logged as `stopping failed`, and the exit status is 1 unless it was already another.
- **Work that outlived a stop could reach a closed store.** `src/store/lmdb.ts`, `src/node/node.ts`,
  `src/node/memory.ts`, `src/sync/blocksync.ts`, `src/consensus/consensus.ts`. Stopping consensus
  and block sync does not end work of theirs that is suspended on a signature verification or on a
  request to a peer, and the RPC server's stop waits one second at most for its methods; whatever
  resumed after `stop()` had closed the store called into the native library on an environment that
  was gone. There are now two guards. `LmdbEnv` throws `StoreClosedError`, `the store is closed`,
  from every `get`, `range`, `write`, `store()` and `transaction()` from the moment `close()` is
  called (`assertOpen`), so such a call fails in JavaScript. And the places known to wait check
  first: `BlockSync.backfill` returns after each of its waits (the block request, the validator set
  request, the commit verification) if block sync was stopped, and `Consensus.handleProposal`
  returns if consensus was stopped while the proposal's signature was verified, before the checks
  that read stored blocks. A stop could also overtake a start and leave what the start went on to
  begin running over the closed store. `start()` is now one promise
  (`this.starting ??= this.startUp()`); `startUp` marks the network as started before it waits for
  it, so a stop during that wait stops the network, and after each wait (the network, the
  collection, the memory guard's first sample) it goes no further if a stop has begun. `shutDown`
  waits for a start still on its way before its other steps. `MemoryGuard` has a `running` flag, so
  a listener that stops the guard during its first sample leaves it stopped and no timer is set
  afterwards. The test `does not go on starting once it is being stopped, and answers a closed
  store with an error` starts and stops a node at once, finds consensus, block sync and the guard's
  timer stopped and the claim gone, reads and writes the block store and gets `StoreClosedError`,
  and stops a guard from its own listener.
  The store's check was then carried further and the node's handlers were given an end.
  `LmdbStore.range` steps the lmdb-js iterator by hand and checks that the environment is open
  before every step, not only when the iteration begins, so an iteration begun before a close and
  stepped after it throws `StoreClosedError` at that step; left early, it gives the cursor back
  unless the environment is closed. The writer `LmdbStore.write` hands its callback is good only
  during the callback: `put` or `del` on a writer kept and used afterwards throws `a store writer
  was used after its write() returned`, and both check that the environment is open. In
  `src/node/node.ts` the handlers for a peer's proposal, vote, fetched block, transaction item and
  evidence item no longer drop their promises with `void`. Each hands its promise to `detached(work,
  what)`, which takes whatever the work ends with and logs `handling a <what> failed`, at `warn`
  while the node runs and at `debug` once it is stopping. Work that was waiting on a verification
  when the node stopped resumes to a closed store (`StoreClosedError`) or a closed verifier pool,
  and that is the end of it, not a rejection nobody handles. The test `refuses every step of an
  iteration and every use of a writer once the disk environment is closed` keeps a writer past its
  `write` and finds it refused, steps an iteration once, closes the environment and finds the next
  step, a `get`, a new iteration, a `write` and a `transaction` each throw `StoreClosedError`.
- **`Node.create` leaked what it had opened when `init` failed.** `src/node/node.ts`. It calls `stop()`
  and rethrows. A constructor that fails cannot wait for a store to close, so it does not clean up on
  the spot: it throws a `ConstructionFailure` carrying the original error and an async `cleanup`, and
  `Node.create` awaits the cleanup and then throws the original error. The cleanup closes the store if
  it is the node's own or lies in a directory the node claimed, closes a verifier pool the node made,
  and releases the claim last, so the claim is not given up while the store is still closing.
- **The executor pruned with the evidence age of the commit before.** `src/node/node.ts`.
  `evidenceAge()` reads the application's unbonding period each time it is asked (unless the operator
  set `limits.maxEvidenceAgeMs`), so a block that lengthens the period is pruned behind with the new
  age.
- **A failed application commit left the chain's writes in place.** `src/node/executor.ts`,
  `src/app/core/app.ts`. Under a shared transaction the executor calls an application's `commitSync()`
  when it has one and `commit()` otherwise, inside the transaction; `CoreApp.commit` is not an async
  function, so a store write that fails throws there and aborts the block's, the validator set's and
  the chain state's writes too, and `applyBlock` rejects with the state unchanged.
- **The memory environment's transaction took nothing back.** `src/store/kv.ts`.
  `MemoryEnv.transaction` only called its callback, so on a node without a data directory the chain's
  batch stayed when the application's commit threw. It now undoes, in every store of the environment,
  the writes made inside a callback that throws: each `MemoryKv` keeps what every key held before
  (`begin`, `end`), a store first asked for inside the transaction is part of it, and a transaction
  inside one joins it. A transaction inside another that throws is undone by itself: it takes a mark in
  each store (`mark`) and, before rethrowing, rolls every store back to its mark (`rollbackTo`, which
  `end` now uses too), a store first asked for inside it going back to nothing. An outer transaction
  that catches the error and goes on keeps only its own writes, as an LMDB child transaction leaves
  its parent. The test `undoes the writes of a memory environment transaction that throws, in every
  store` has a part for the inner failure.
- **A past height's validator set came with a later proposer.** `src/node/executor.ts`.
  `validatorSetAtHeight` read every height but the three the state holds from the record by hash,
  which later heights with the same set rewrite, so the RPC's `validators` named a proposer that was
  not that height's. It reads the record by height first (`loadValidatorsAt`), the set as that height
  had it, and the record by hash only where that one is gone or never was: a block pruned, a block
  backfilled below a state-sync join, a header kept alone. Members and powers are the same either
  way. A backfilled block and a header kept alone have only the set by hash, whose proposer is still
  a later height's: `hasProposerAt(h)` is true for the three sets the state holds or when the record
  by height exists, and where it is false the RPC's `validators` returns `proposer: null` instead of
  that later proposer.
- **Pruning was not one transaction, and validator sets by height were never pruned.**
  `src/node/executor.ts`, `src/store/blockstore.ts`. Each pass of `pruneBlocks` and of `pruneHeaders` is
  one `store.batch`, the deletions with their marker; `deleteBlock` deletes the set stored under its
  height in the same write.
- **A transaction repeated in one block was indexed at its first position.** `src/store/blockstore.ts`.
  `saveBlock` indexes it once, at the first position where it succeeded, otherwise at its first.
- **The memory store applied deletes before puts.** `src/store/kv.ts`. `MemoryKv.write` applies the
  operations in the order made, as LMDB does.
- **`--max-old-space-size=0` was read as a limit of zero.** `src/node/memory.ts`. `heapLimitFlag` reads
  it as no flag.
- **Gossiped evidence was pooled whatever its age.** `src/node/node.ts`. `acceptEvidence` checks it with
  `evidenceAgeOk` (the next height, the last block's time) before verifying; evidence too old, of an
  unknown height or beyond the height being decided is dropped without pooling and without a score.
- **An `item` nobody fetched was processed.** `src/node/node.ts`. An item is processed only if its hash
  was fetched from that peer as that kind; otherwise it is dropped unread, without a score.
  `itemNotFound` takes only the peer that sends it out of a fetch. After 10 s without an answer the
  item may be fetched from another peer too, four at most; a peer already asked is skipped and does
  not move that time. A fetch is remembered by kind and hash, so an announcement of one kind cannot
  block the other's, for one minute from its first sending whatever is asked after, by a clock that
  does not go back (`performance.now()`), and an answer is taken only within that minute. A node
  remembers 20,000 fetches at most and 2,048 for one peer, which is asked nothing more until answers
  or expiry free places, so a peer that announces and never answers cannot make it remember without
  limit. When the 20,000 are in use only the hash there is no place for is passed over, not the rest
  of the announcement, and a peer that disconnects is taken out of every fetch still outstanding, so
  what it announces after it reconnects is asked for again.
- **The 16 pieces of evidence a block may carry were a proposer's habit.** `src/consensus/validate.ts`.
  `MAX_EVIDENCE_PER_BLOCK` is exported from there and `validateBlockStructure` refuses a block with more
  (`too much evidence`): a rule of the chain.
- **The block size was a setting of each node.** `src/types/genesis.ts`, `src/node/node.ts`.
  `validateBlockStructure` applies `maxBlockBytes` to proposals, to blocks being committed and to
  synced blocks, so two nodes configured differently would have disagreed about which blocks are
  valid. It is now `consensus.maxBlockBytes` in the genesis, a whole number from 65,536 to 16,777,216
  (`checkMaxBlockBytes`) and 4 MiB when absent; `Node.init` takes it from there alone and
  `NodeConfig.limits` no longer carries it. `init --max-block-bytes <n>` (`src/cli.ts`) writes it
  into the genesis it makes, checking it first with `checkMaxBlockBytes`, so that a refused value
  writes nothing; without the flag the genesis has no such field. The mempool's transaction limit follows it: the smaller of
  1 MiB and four bytes under half the block size. A limit on the whole encoded block could be one no proposer can
  meet: with 64 KiB blocks and 40 ML-DSA-44 validators the commit alone makes an empty block 65,781
  bytes, so every proposal would be invalid and the chain would stop. The limit is therefore on what
  the proposer chooses: `blockDataBytes` (`src/types/block.ts`) is the encoded size of the
  transactions and the evidence, `validateBlockStructure` refuses a block in which it exceeds
  `maxBlockBytes` (`block too large`), and the builder gives the transactions the limit less the
  evidence and 1 KiB, dropping the last piece of evidence while evidence and that 1 KiB exceed half
  of it (the shell it measured before, finding 56, is gone). An empty block is always within the limit. So
  that a block still fits a network frame with the two commits it travels with, a validator set holds
  at most 2,000 members (`MAX_VALIDATORS`, `src/types/validator.ts`): the `ValidatorSet` constructor
  throws `N validators exceed the limit 2000` and `decode` bounds its list by it, where it allowed
  10,000. Evidence was at first allowed the whole limit. With a 64 KiB limit a transaction of 32,768
  bytes was then admitted, thirteen ML-DSA-44 evidence records (about 4.9 KiB each) left it no room,
  and evidence arriving with every block could have kept it, and everything queued behind it, out for
  ever. So evidence takes at most half a block, the transactions always get at least half, and the
  mempool's `maxTxBytes` is `min(1 MiB, floor(maxBlockBytes / 2) - 4)`, the 4 being the transaction's
  length prefix in the block: a transaction the pool admits fits the next block it is first in line
  for, whatever evidence is waiting. With the default 4 MiB nothing changes in practice, sixteen
  records being about 79 KiB. `maxClockDriftMs` stays a node's own setting, which is right: it is
  applied only to a fresh proposal when the node decides its prevote, never to a block being committed
  or synced, so it is a rule for what a node votes for, like its clock, and cannot divide the chain.
- **Validator sets by hash were never removed.** `src/node/executor.ts`, `src/store/blockstore.ts`.
  After a pruning pass has removed blocks and headers, `pruneValidatorSets` deletes
  (`deleteValidatorSet`) each set whose hash the removed heights carried, unless a header still held
  names it as `validatorsHash` or `nextValidatorsHash` or the current state uses it. The usual case is
  settled by the first header looked at, and a reference found is remembered (`setNamedAt`).

- **Two immediates could run after a stop.** `src/node/node.ts`, `src/sync/blocksync.ts`. The node
  queued a collection with `setImmediate` after every commit, and block sync queued its next
  backfill step the same way; neither kept what it had queued, so either could run once `stop()`
  had returned. The backfill step returned on its first line, seeing `running` cleared; the
  collection ran, and could start a major one on a stopped node. The node now keeps its immediate
  in `afterCommit`, one at a time, queues none once it is stopping, and clears the one queued at
  the start of `shutDown`, before its first wait. Block sync keeps its own in `nextBackfill`, and
  `stop()` clears it. The test `leaves nothing queued behind a stop made from a commit, and no file
  open behind a genesis that does not parse` (its first half) stops a node from a commit listener
  that runs after the node's own: the scheduler is not called after the stop, and both fields are
  null.

### Object database, application and codec

- **The account history log kept its count of a write that failed.** `src/app/core/history.ts`,

  from the store again; `CoreApp.persist()` calls it when the store write fails and rethrows. The block
  is kept, so `commit()` called again writes it with a correct history, and the list of stale history
  versions is cleared only after a write that succeeded. The comment on when the heads are written
  after a widening was corrected.
- **A failure while the root was taken left the block's changes in memory with nothing said.**
  `src/app/core/app.ts`. A failure after the block's session is committed marks the application failed:
  `finalizeBlock` throws and `checkTx` answers not ok with `the application failed while taking the
  root of block N (cause) and holds changes it cannot undo: restart the node, the store has the state
  of the block before`; `commit()` then writes nothing. A failure while the session is open is undone as
  before.
- **`commit()` was async.** `src/app/core/app.ts`. A failed store write throws where `commit()` is
  called; a snapshot that fails after the write rejects the promise as before.
- **A validator slashed of its whole stake took delegations.** `src/app/core/staking.ts`. `bond()`
  refuses with `validator has lost all its tokens to slashing and takes no delegation` when the tokens
  are 0 and shares are outstanding, for a delegation and for a redelegation into it.
- **An account could be given an authority no key leads to.** `src/app/core/evaluate.ts`.
  `checkNewAuthority`: when the authority's own keys do not reach the threshold, every key reachable
  through the member accounts, to the depth limit, is collected and the authority must be satisfied
  with all of them signing, else `authority can never be satisfied: its member accounts do not lead to
  keys enough for the threshold`. When more than 16 keys count toward the authority, the cheapest way
  to the threshold (`minSignatures` in `src/app/core/authority.ts`: a key costs one signature, a
  member account what its active authority costs) must fit in the 16 signatures a transaction
  carries, else `authority can never be satisfied: it needs more than the 16 signatures a transaction
  can carry`. It applies to `accountCreate` and to `accountUpdate`, which is judged against the
  account as the update leaves it.
- **`getCommitted` fell back to the live object for a write made outside a session.**
  `src/db/database.ts`. `getCommitted`, `committedNextInstance` and `bytesIn` read the root shadow
  first: they answer as of the last `root()` whatever was written since.
- **A database with more than 511 types failed when its trees were dropped.** `src/db/database.ts`,
  `src/db/merkle.ts`. The constructor refuses them (`N object types: a database holds at most 511`).
- **The arena's comment promised a hard copying budget.** `src/db/arena.ts`. The comment on `maintain`
  says what the code does: no further slab is started once the budget is reached, and one that was
  started is finished.
- **A sparse tree kept its caller's value buffer.** `src/db/smt.ts`. `set()` copies the value.
- **More than 16 authenticated indices could be defined and not decoded.** `src/db/proof.ts`,
  `src/db/index.ts`, `src/app/core/snapshot.ts`. `MAX_AUTHENTICATED_INDICES` is used by `decodeProof`,
  `decodeKeyProof` and `decodeManifest`, and a type with more is refused when its index is made.
- **`Reader.fixed()` and `bytes()` returned a view of a `Buffer`.** `src/codec/reader.ts`. Both return a
  plain `Uint8Array` copy whatever was passed.
- **A `Writer` made with no capacity never grew.** `src/codec/writer.ts`. `ensure()` grows from at
  least 16 bytes.
- **The test application lost its validators at a restart and passed updates the engine halts on.**
  `src/app/kvstore.ts`. Its snapshot file keeps the validators, and a file without them is refused by the
  constructor (`<file> was written before the validator set was kept in it and cannot be used: remove
  the data directory and sync again`); `finalizeBlock` tries each `val:` transaction against a working copy of the set and fails one
  that removes an unknown validator, removes the last one (`the last validator cannot be removed`),
  adds one to a set that already holds `MAX_VALIDATORS` (`the set already holds the limit of 2000
  validators`) or takes the total power past `MAX_TOTAL_POWER`; a validator added and removed in one block gives no
  update. A `val:` transaction whose key is of another signature scheme than the set's keys is refused
  by `parse` (`key must be a <scheme> key`), in `checkTx` and in a block, where `nextState` would
  have halted on the update.
- **A genesis validator with too small a balance failed with a transaction's error.**
  `src/app/core/staking.ts`. `bootstrapValidators` reports it as `genesis validator <name>: <name> has
  insufficient <symbol>`, an `Error` like the checks beside it, where the `TxError` of `adjustBalance`
  came through.

### RPC, CLI, wallet and light client

- **A stopped RPC server stayed subscribed to the executor.** `src/rpc/server.ts`, `src/rpc/events.ts`,
  `src/node/executor.ts`. `BlockExecutor.onCommitted` returns a function that removes the listener;
  `RpcServer.stop` closes its `RpcEvents`, which takes its callback back, answers every commit-mode
  wait with null at once and gives out no new wait.
- **A stopped RPC server could leave a method running over stores about to be closed.**
  `src/rpc/server.ts`. Closing a connection does not end the method its request called: a broadcast
  waiting on the mempool resumed after `stop` had returned and read the node's stores, which the
  caller of `stop` might have closed by then. `stop(graceMs)` now sets `stopped`, and after the
  connections are closed it waits, one second at most, for the requests still being handled
  (`inFlight`, each until its method has returned and its answer is written). A request that reaches
  dispatch once the server is stopping is answered with code -32000, `server is stopping`, and its
  method is not called. The test `is stopped only once the methods it was running have returned`
  stops a server while a method sleeps and finds the method ended when `stop` returns. A stop that
  overtook a `start()` closed a server that was not yet listening, which then listened all the same;
  `start()` now keeps its promise in `starting` and `stop` waits for it before closing (test
  `is not listening after a stop that overtook its start`), and the command line's `start` returns on
  seeing `stopping` after the server's start as it does after the node's. That holds
  for a method that ends within the second. One that takes longer is not cancelled: `stop` returns
  without it, and when it next touches the store of a node that has stopped it gets
  `StoreClosedError` (the item "Work that outlived a stop could reach a closed store" above), which
  its handler turns into an error answer on a connection already cut.
- **The status line could read the application after its store was closed.** `src/cli.ts`. `start`
  logs a status line every five seconds from an interval nobody kept, and the line reads the
  application (`app.dynamic()`). A tick that came while the node was shutting down, after the store
  was closed, got `StoreClosedError` inside a timer, where no handler stands, and the process ended
  on that error and not with the code the shutdown was given. The interval is now kept in `status`,
  and `shutdown()` clears it first, before anything is stopped. A shutdown that
  begins before the interval exists, while the node's or the RPC server's `start()` is still awaited,
  has nothing to clear, and `start` returns on seeing `stopping` after either without setting it.
  `test/review5-rpc.test.ts`, "writes the block size it was given into the genesis, and runs a node
  that stops on a signal with its directory released", runs `start` as a child process under the
  heap wrapper, waits for a status line, sends `SIGINT` and expects exit code 0, the `LOCK` file gone
  and no `stopping failed`, `start failed` or `the store is closed` in the output: a node that has
  run past a status tick stops by signal with the code the shutdown gave it. The test does not make
  a tick fall during the shutdown, so it would not by itself fail with the interval left running;
  no test forces that.
- **A replayed block event lacked `failed`.** `src/rpc/events.ts`. `blockEventJson(block, results)`
  makes the live and the replayed event alike; on replay `failed` is counted from the stored results,
  null for a block with transactions whose results the node does not hold, 0 for an empty block.
- **`/events?account=<id>` opened a stream for an id no account has.** `src/rpc/server.ts`. The id must
  be an existing account's, else 404 as for an unknown name.
- **Names every object inherits were found where none was stored.** `src/wallet/keystore.ts`,
  `src/rpc/server.ts`, `src/cli.ts`. The keystore's `keys` is an object without a prototype and `has`,
  `add` and `remove` use `Object.hasOwn`; the RPC's method lookup uses it too, so `toString` answers
  `-32601`; so do the path segments of the CLI's `propose`.
- **A validator could not be named by its operator's account id.** `src/rpc/methods.ts`. `validatorRef`
  resolves a numeric id of the account type through the operator index at the height asked, as it does
  a name; an account running no validator is `-32001`, `<id> runs no validator`.
- **The comment on a malformed request said it is always answered under a null id.**
  `src/rpc/server.ts`. It says what the code does: under its own id when that can be read.
- **The CLI's usage line was unreachable, `whole()` printed `12.0` for precision 0, `light.json` named no
  chain, and `verify-tx` said `result not yet committed` for a block without results.** `src/cli.ts`.
  The commands that take a target are checked before the target is resolved, and no command or an
  unknown one prints the usage and exits 1; an amount at precision 0 prints as `12`; `light.json` is
  `{ chainId, height, hash }` and one of another chain is refused by name, while a file without the
  chain id is accepted and written back with it; `verify-tx` on a block whose results the node lacks
  prints `included at height H; this node does not hold the results of that block`.
- **The CLI passed an empty argument on.** `src/cli.ts`. `need` refuses an empty string as it does a
  missing argument (`missing <what>`), for every command, so `keys add ''` no longer reaches the
  keystore, which still refuses an empty name for its other callers.
- **The light client's trusting period at verification time had no test.** `test/review5-rpc.test.ts`.
  A case on an injected clock covers the next header, a later one and `verifyLatest`.
- **The network benchmark skipped the app hash comparison when heights differed.**
  `bench/network.bench.ts`. The synced node is stopped, the benchmark waits up to 30 s for a validator
  to hold the block after the synced node's height and compares the synced app hash with that header's;
  it throws on a disagreement and never skips. The recorded run in docs/benchmarks.md predates this.
- **The empty-block benchmark gave one of two results by chance.** `bench/app.bench.ts`. It timed 20
  empty blocks straight after the full ones and came out at about 175 microseconds or about 450 from run to
  run. The cause is the state of the JavaScript engine's compiler, not the chain: the functions an
  empty block runs are compiled for what the full blocks did, the first twenty or so empty blocks run
  that code, then it is discarded and they run unoptimised until, about 600 blocks on, it is compiled
  again; with the optimising compilers switched off the time is flat. The benchmark now runs 1,000
  empty blocks before it measures 500: 286 microseconds under ML-DSA-44 and 290 under secp256k1
  (docs/benchmarks.md).

### What remains

- The data directory's claim trusts the pid in `LOCK`: a pid given since to an unrelated process makes
  a stale claim look live. A process killed in the few file operations for which it holds
  `LOCK.takeover` leaves that file behind, and it has to be removed by hand. One killed between writing
  its private `LOCK.<pid>.<8 hex>` file and unlinking it leaves that file, which is harmless and can be
  deleted, and the directory must be on a filesystem that has hard links. An operating system file
  lock would close all of these. The claim stays a file because Node's standard library has no lock
  the operating system holds; these residues follow from that.
- When two nodes dial each other and the inbound connection survives, the dialed address is dialed
  again, with backoff. A peer's advertised address and the name it was dialed by are separate records.
- Four validators that sign proposals for rounds that will not come can still fill the buffer of
  next-height proposals; a proposal not held is sent again by gossip while its round lasts.
- Heights a pruning node deleted under a shorter unbonding period are gone: until a full new window
  has passed after the period is lengthened, it refuses evidence that names them.
- After a commit that was aborted, or a failure while a root is taken, the application's memory holds
  a block the store does not, and the node needs a restart.
- The sets by height below the lowest block in a store pruned before this pass stay, and so do the
  sets by hash that only heights pruned before it carried.
- A later `accountUpdate` of a member account can still leave another account's authority with no keys
  that reach its threshold, or needing more than 16 signatures. It is not checked again on purpose:
  refusing a member's update because of the accounts that name it would let anyone constrain another
  account's keys by naming it in an authority of their own. An authority that rests on another
  account takes that risk. The count of signatures an authority needs
  takes a key shared by two member accounts once for each, so it can refuse an authority that shared
  keys would satisfy within 16.
- `changedSince()` does not see an object removed outside a session since the last root; the node
  never writes outside a session.
- The limit on a transaction (the smaller of 1 MiB and four bytes under half the block size) is mempool policy. A
  block's validity bounds a transaction only through the block size, which every node now holds
  alike, so nodes cannot disagree over it.
