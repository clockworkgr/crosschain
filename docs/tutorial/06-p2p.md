# 6. Peer-to-peer networking

This part moves bytes between nodes. It owns the transport (TCP, or an in-process hub for tests), the framing, the wire message set, the authenticated handshake that turns a connection into a peer, the peer database and address exchange, keepalives, duplicate connection resolution, misbehaviour scoring with bans, and a small request/response helper on top of a protocol that has no correlation ids. It uses the [codec](01-codec.md) for every message, the [crypto](02-crypto.md) layer for node identity and the handshake signatures, and the [types](03-types.md) for the proposals, votes, blocks and validator sets it carries. It knows nothing about consensus: the [consensus engine](04-consensus.md), the [mempool](05-mempool-executor.md), [block and state sync](07-sync.md) and the [node](08-node.md) subscribe to message types and decide what to do with them. The design follows Graphene (BitShares): a flat set of peers, one stream each, no channel multiplexing, and inventory gossip for items that are not time-critical.

## Concepts

**A transport abstraction.** `src/p2p/transport.ts` defines two small interfaces: a `Transport` that can `dial` an address and `listen` on one, and a `Conn` that sends and receives whole frames and reports when it closes. Everything above those two interfaces, from the handshake up to consensus, is identical whether the frames travel over a TCP socket or between two objects in one process. DESIGN.md section 4 states the purpose: "one interface, two implementations. TCP via Node net, with manual length-prefix framing. In-memory, linking node instances directly. Supports injected latency, drops, and partitions. Used to run many validators in one process for tests and demos." That last point matters more than it looks. A consensus protocol is only interesting under failure: a validator down, a partition, a message lost. Those are easy to script against an in-memory hub and nearly impossible against real sockets in a unit test. Every network scenario in `test/consensus.test.ts` and `test/sync.test.ts` runs four or five whole nodes inside one vitest process on the memory transport.

**Length-prefixed framing.** TCP delivers a byte stream, not messages: the kernel may hand the receiver half a message, or three messages in one chunk. The sender therefore writes a 4-byte big-endian length before every frame, and the receiver accumulates chunks until it holds `4 + length` bytes, then cuts one frame off the front and repeats. The in-memory transport does not need framing because it delivers `Uint8Array` objects whole, which is exactly why framing lives in `src/p2p/tcp.ts` and not in the `Conn` interface.

**Node identity and the authenticated handshake.** Each node has a long-lived ML-DSA-44 node key, separate from any validator key. Its node id is the SHA-256 of the public key (`addressOf` in `src/crypto/keys.ts`), printed as hex. When two nodes connect they run a three-message handshake: the dialer sends `hello`, the acceptor answers `helloAck` carrying its own hello and a signature, and the dialer answers `auth` with its signature. Both sign the same bytes, the dialer's hello followed by the acceptor's hello, and each hello contains a fresh 32-byte random nonce. The signature proves that the party holding the private key of the claimed node id is on the other end of *this* connection: because both nonces are inside the signed bytes, a signature captured from an earlier session cannot be replayed, and because the chain id is inside the hello and also in the signing context (`"<chainId>/p2p"`), a signature made for one chain cannot be reused on another. There is no key exchange and no encryption. DESIGN.md section 3: "Transport: authenticated, not encrypted. Every consensus message and tx is independently signed, so confidentiality adds nothing. X25519 is dropped entirely." What the handshake does not protect against is an active attacker on the path dropping or delaying frames, which no handshake can prevent; consensus tolerates that as it tolerates any faulty link.

**Flat topology, Graphene style.** CometBFT multiplexes several "channels" (consensus, mempool, blocksync, evidence) with priorities over one connection. Graphene, the BitShares node, has one message stream per peer with a type byte on each message and no channels. This chain takes the Graphene shape because it is simpler: `src/p2p/network.ts` keeps a `Map` of peers, each with a `send(message)` function, and that is the whole API. DESIGN.md section 3: "Topology: flat. One TCP stream per peer, one message type field, no channel multiplexing. After the handshake, inbound and outbound peers are indistinguishable."

**Slots and the eclipse defence.** The one place where direction still matters is counting. A node keeps a target number of *outbound* connections it chose itself (`desiredOutbound`, default 8) and a cap on *inbound* connections others chose (`maxInbound`, default 32). If inbound peers could fill every slot, an attacker who dials a node from many addresses could surround it and feed it a false view of the chain, the "eclipse" attack. By always keeping self-chosen outbound connections, the node always has some peers the attacker did not pick. DESIGN.md: "minimum self-chosen outbound connections is enforced so inbound peers can never occupy every slot (eclipse defense). Slot accounting is not symmetric even though message handling is." An inbound handshake still in progress holds a slot as well (`pendingInbound`, below): a cap that counted only finished handshakes would let a burst of simultaneous dials all pass it at once.

**Peer exchange and the peer database.** Nodes learn addresses from each other. Right after the handshake each side sends `addrRequest`; the reply carries the listen addresses of current peers plus a sample from the database. The database (`src/p2p/peerdb.ts`) is modelled on Graphene's `potential_peer_db`: a record per address with success and failure counts, last attempt and last seen times, and an optional ban. The connect loop draws candidates from it with exponential backoff after failures, and persists it as JSON because nothing in it is hashed or signed (the rule in DESIGN.md section 4 is that JSON is "not used for anything that gets hashed or signed"; peer records qualify).

**Duplicate connections.** Two nodes that know each other's address may dial each other at the same moment, which yields two connections to the same node id. Both sides must agree on which one to keep without talking about it. The rule: if both connections are young, keep the one *initiated by the lower node id*, which both sides can compute from the two ids alone. If the existing connection is old (more than two seconds), the peer has probably restarted and its old socket has not timed out yet; the new connection wins so a restarted validator rejoins at once.

**Two gossip modes.** Items that are not urgent, transactions and evidence, use *inventory* gossip: a node announces hashes (`inv`), a peer asks for the ones it lacks (`fetch`), and the announcer sends the bytes (`item`) or says it no longer has them (`itemNotFound`). This is Bitcoin's `inv`/`getdata` and Graphene's `item_ids_inventory`/`fetch_items`, and it stops every node from receiving every 2.5 KB transaction from every peer. Items that are urgent, proposals and votes, are *pushed* directly, because an inventory round trip on each of the three Tendermint phases would add latency to every block. DESIGN.md section 3 lists both modes and the re-send rule that goes with push. Committed blocks are neither pushed nor announced by hash: a `status` message carries the height, and a lagging peer pulls blocks through block sync. The network layer only defines these messages; which to send when is decided in `src/node/node.ts` (see [the node](08-node.md)).

**Scoring and bans.** A peer that sends something malformed, invalid or abusive is charged points. Points decay by one per minute; at 100 the peer is disconnected and its node id is banned for an hour, doubling on each repeat, and so is its address if this node dialled it. An address a peer merely advertised is a claim, not an identity, and is never banned on the peer's own word. RPC-SYNC-PROOFS.md section 4.6 fixes the tariff: "bad signature 20, malformed message 20, failed proof or chunk 50, bad block during sync 50, unsolicited or duplicate flood 5." DESIGN.md section 3 places it in the history of the design: "Scoring and bans came with stage three (section 9)." The network layer owns the ledger (`Network.score`); the callers decide what counts as an offence.

**Request and response without correlation ids.** The wire protocol has no request id field. A caller that sends `blocksRequest { from: 10, count: 8 }` and wants the matching `blocksResponse` registers a predicate ("the response whose `from` is 10") on the response type from that peer, with a timeout. `src/p2p/request.ts` keeps those pending predicates and settles the first one that matches. It is small because the protocol was designed so that every response echoes enough of its request to be matched.

**Keepalive.** Every `pingIntervalMs` a node pings each peer with the current time; the pong echoes it, which yields a round-trip latency. A peer from which nothing has arrived for `idleTimeoutMs` is dropped. DESIGN.md also mentions a clock offset per peer; the code computes only latency.

## The code, file by file

### src/p2p/transport.ts

The interfaces every other file in this part builds on, plus a base class that implements the buffering both transports need.

```ts
export interface Conn {
  readonly remoteAddr: string;
  send(frame: Uint8Array): void;
  /** Replaces any previous handler. Frames that arrive before a handler is set are buffered. */
  onFrame(cb: (frame: Uint8Array) => void): void;
  onClose(cb: (err?: Error) => void): void;
  close(): void;
  readonly closed: boolean;
}

export interface Transport {
  dial(addr: string): Promise<Conn>;
  listen(addr: string, onConn: (conn: Conn) => void): Promise<void>;
  close(): Promise<void>;
}
```

`Conn` is a bidirectional frame pipe. `send` takes whole frames and never blocks or throws; `onFrame` installs the single receive handler and *replaces* any previous one, which the handshake relies on (it swaps handlers at every step); `onClose` installs the single close handler; `close` tears the connection down; `closed` says whether it has been. `remoteAddr` is whatever the transport knows about the other end: for TCP the socket's remote host and port, for the memory hub the name the other side registered under.

`Transport` has `dial`, which resolves with a connected `Conn` or rejects; `listen`, which binds and hands every accepted connection to `onConn`; and `close`, which stops listening.

**`BaseConn`** is the abstract class both `MemoryConn` and `TcpConn` extend. It handles three things that would otherwise be duplicated and are easy to get wrong:

- Frames that arrive before any `onFrame` handler is installed are queued in `pending` and flushed, in order, when the handler is set. Without this, a frame delivered in the gap between `dial` resolving and the caller installing a handler would vanish. The memory transport hits this gap on every connection: the dialer's first `hello` is often delivered before the acceptor's handshake code has run.
- `deliver(frame)` drops frames after `closed` is set.
- `markClosed(err)` is idempotent and delivers the close callback exactly once (`closeDelivered`), whether the callback was installed before or after the close happened.

```ts
  onFrame(cb: (frame: Uint8Array) => void): void {
    this.frameCb = cb;
    const queued = this.pending;
    this.pending = [];
    for (const f of queued) cb(f);
  }
```

and, on the receiving side:

```ts
  protected deliver(frame: Uint8Array): void {
    if (this.closed) return;
    if (this.frameCb) this.frameCb(frame);
    else this.pending.push(frame);
  }
```

Subclasses implement `remoteAddr`, `send` and `close`, and call `deliver` and `markClosed`. Note that `pending` is unbounded: a peer that sends before the handshake installs a handler can queue frames here, but the handshake installs one immediately after dial or accept, so the window is a few microseconds.

### src/p2p/memory.ts

The in-process transport. A `MemoryHub` is a registry of listeners by name; dialing a name creates a pair of connected endpoints.

**`MemoryHub`** exports:

- `latencyMs`: a delay applied to every frame delivery, every accept and every close propagation. Tests set it to 1 to 20 ms; `scripts/localnet.ts` sets 5 ms.
- `messageFilter`: an optional predicate `(from, to, frame) => boolean`; returning false drops the frame. `test/sync.test.ts` uses it to drop every `proposal` destined for one validator and watch it decide heights anyway by fetching the block its peers precommitted.
- `partition(groupA, groupB)`: blocks every frame between any address in A and any in B, both directions. `isolate(addr, others)` cuts one address off. `heal()` clears every block. `isBlocked(from, to)` is the query the connections use.
- `transport(addr)`: returns a `Transport` bound to the local name `addr`.

```ts
  transport(addr: string): Transport {
    const hub = this;
    let bound: string | null = null;
    return {
      async dial(target: string): Promise<Conn> {
        const accept = hub.listeners.get(target);
        if (!accept) throw new Error(`connection refused: ${target}`);
        const [a, b] = MemoryConn.pair(hub, addr, target);
        setTimeout(() => accept(b), hub.latencyMs);
        return a;
      },
      async listen(bind: string, onConn: (conn: Conn) => void): Promise<void> {
        if (hub.listeners.has(bind)) throw new Error(`address in use: ${bind}`);
        hub.listeners.set(bind, onConn);
        bound = bind;
      },
      async close(): Promise<void> {
        if (bound !== null) hub.listeners.delete(bound);
        bound = null;
      },
    };
  }
```

Three things to notice. `dial` resolves with endpoint `a` at once but hands endpoint `b` to the listener only after `latencyMs`, so a dialer typically sends `hello` before the acceptor has seen the connection; `BaseConn.pending` holds it. `dial` to a name nobody listens on fails with `connection refused`, which is what a real dial to a closed port does, and the peer database records it as a failure. `close` removes exactly the listener that `listen` registered: the transport remembers the bound name in `bound` and forgets it on close, so even a transport that listened under a name other than its own `addr` leaves nothing behind.

**`MemoryConn`** (not exported) is a `BaseConn` with a `peer` field pointing at the other endpoint. `pair` creates two and cross-links them. `send` returns silently if the connection is closed, if the hub blocks this direction, or if the filter rejects the frame; otherwise it schedules delivery of a *copy* of the frame (`frame.slice()`, "as over a wire: the receiver's bytes are its own") after the latency. Without the copy a sender that reused its buffer, or a receiver that decoded in place, could change bytes the other side still held, something TCP never allows, and the in-process tests would pass behaviour the real transport does not have. `close` marks itself closed now and the peer closed after the latency, so a close is observed by the remote side with the same delay as a frame. Partitions are enforced per direction in `send`, and `partition` adds both directions, so a partition drops the pings too; the keepalive loop then drops the peer after `idleTimeoutMs`, which is what the test `drops a peer that goes silent` checks.

### src/p2p/tcp.ts

The real transport on `node:net`.

```ts
/** Bytes queued for one peer before we give up on it. */
const MAX_BUFFERED = 32 * 1024 * 1024;
const MAX_FRAME = 32 * 1024 * 1024;
```

`parseAddr(addr)` (not exported) splits at the last colon, defaults the host to `0.0.0.0`, rejects a missing or out-of-range port, and strips the square brackets of an IPv6 literal, so `[::1]:26656`, the form `PeerDb.isValidAddr` accepts, reaches `net.connect` as the bare host `::1`.

**`TcpConn`** (not exported) wraps a `Socket`. The constructor records the remote address as `host:port`, turns off Nagle's algorithm (`setNoDelay(true)`, so small consensus messages go out immediately), and hooks `data`, `error` and `close`. The framer is `onData`:

```ts
  private onData(chunk: Buffer): void {
    this.chunks.push(chunk);
    this.buffered += chunk.length;
    while (true) {
      if (this.buffered < 4) return;
      // Chunks are joined only once a whole frame is in, so a frame arriving in many pieces costs linear work.
      if (this.chunks[0]!.length < 4) this.chunks = [Buffer.concat(this.chunks)];
      const len = this.chunks[0]!.readUInt32BE(0);
      if (len > MAX_FRAME) {
        this.close();
        return;
      }
      if (this.buffered < 4 + len) return;
      const buf = this.chunks.length === 1 ? this.chunks[0]! : Buffer.concat(this.chunks);
      const frame = new Uint8Array(buf.subarray(4, 4 + len));
      const rest = buf.subarray(4 + len);
      this.chunks = rest.length > 0 ? [rest] : [];
      this.buffered = rest.length;
      this.deliver(frame);
    }
  }
```

Chunks accumulate until at least a header is present. The header is read from the first chunk alone; only when that chunk is shorter than four bytes are the chunks joined early. A length above 32 MiB closes the connection (a peer cannot make the receiver allocate without bound by announcing a huge frame). Then nothing more happens until `buffered` covers the whole frame; at that moment the chunks are joined once, the frame is copied out (`new Uint8Array(...)` copies, so the frame does not pin the socket buffer), the remainder becomes the single buffered chunk, and the loop continues, because one chunk may hold several frames. Joining only when a frame is complete is what keeps reassembly linear. An earlier version concatenated every chunk held so far on every `data` event, so a frame arriving in `n` pieces was copied about `n` times over, quadratic in its size: a peer sending a large frame in small writes could keep a core busy for the whole transfer. Now each byte is copied a bounded number of times whatever the chunking. The frame is handed to `BaseConn.deliver`.

`send` is the other half:

```ts
  send(frame: Uint8Array): void {
    if (this.closed) return;
    // A peer that stops reading must not make us buffer without bound.
    if (this.socket.writableLength > MAX_BUFFERED) {
      this.close();
      return;
    }
    const header = Buffer.alloc(4);
    header.writeUInt32BE(frame.length, 0);
    this.socket.write(Buffer.concat([header, Buffer.from(frame)]));
  }
```

The `writableLength` check is the fix for finding 14 of REVIEW-2026-10-28.md, which showed that a peer could request the same transaction ten thousand times while reading slowly and make the server buffer responses until memory ran out. Now a peer with 32 MiB of unread output is dropped. `close` destroys the socket and marks the connection closed; a socket `error` also closes it, with the error passed to the close callback.

**`TcpTransport`** implements `Transport`. `dial` connects and resolves with a `TcpConn` on `connect`, rejecting on an `error` before that (the one-time error listener is removed once connected so later errors go to the `TcpConn` handlers). `listen` creates a server, wraps each accepted socket in a `TcpConn`, and resolves once bound. `close` closes the server and waits for it. The test `handshakes over real sockets and delivers framed messages` runs two networks on ports 38881 and 38882 of localhost.

### src/p2p/messages.ts

The wire vocabulary. A frame is one type byte followed by the payload, written with the [codec](01-codec.md). Proposals, votes, blocks, commits, headers and validator sets are encoded with the same functions used to hash and sign them, so "the bytes on the wire are the bytes that were signed" holds by construction.

Exports:

- `NONCE_SIZE = 32`.
- `Hello`: the handshake record: `chainId`, `publicKey` (1312 bytes), `nonce` (32 bytes), `listenAddr` (`''` when the node accepts no inbound connections), `height` (last committed), `userAgent`.
- `RejectCode`: `WrongChain: 1, Self: 2, AlreadyConnected: 3, NotAccepting: 4, Invalid: 5`. `AlreadyConnected` is defined but never sent; the network resolves duplicates by closing a connection after establishment rather than by rejecting during the handshake.
- `InvKind`: `Tx: 1, Evidence: 2`, the item kinds of inventory gossip.
- `MAX_HEADERS = 1000`: the most headers one `headersResponse` carries, and the decoder's limit on it.
- `Message`: the discriminated union of every message; `MessageType` its `type` field.
- `encodeHello`, `decodeHello`, `helloBytes`: the hello codec and its standalone encoding.
- `handshakeSignBytes(helloInitiator, helloAcceptor)`: the bytes both sides sign.
- `encodeMessage(m)` and `decodeMessage(buf)`: the frame codec.

The signed bytes:

```ts
/** Both sides sign the same bytes: the initiator's hello then the acceptor's. The nonces inside bind it to this session. */
export function handshakeSignBytes(helloInitiator: Hello, helloAcceptor: Hello): Uint8Array {
  return encode((w) => {
    w.bytes(helloBytes(helloInitiator));
    w.bytes(helloBytes(helloAcceptor));
  });
}
```

Each hello is written with `w.bytes`, which prefixes a length, so the boundary between the two hellos is unambiguous and no field of one can be shifted into the other.

Every message type, its code, its payload, who sends it and why:

| type | code | payload | sent by | purpose |
|---|---|---|---|---|
| `hello` | 1 | `Hello` | dialer | first handshake message |
| `helloAck` | 2 | `Hello`, `signature` (2420 bytes) | acceptor | its hello plus a signature over both hellos |
| `auth` | 3 | `signature` | dialer | its signature over both hellos; the dialer is a peer once this is sent |
| `reject` | 4 | `code` u8, `reason` string (≤ 1024) | either, during the handshake | why the connection is refused; the sender closes 50 ms later |
| `addrRequest` | 5 | none | both, right after establishment | ask for known addresses |
| `addrResponse` | 6 | `addrs` string[] (≤ 256 entries, each ≤ 256 chars) | the asked peer | listen addresses of its peers and a sample of its database |
| `ping` | 7 | `time` u64 | keepalive loop | sent every `pingIntervalMs` |
| `pong` | 8 | `time` u64 | the pinged peer | echoes the time; the sender computes latency |
| `status` | 9 | `height` u64 | both, at establishment and after every commit | tells peers how far this node is; block sync watches it |
| `inv` | 10 | `kind` u8, `hashes` (≤ 10,000, 32 bytes each) | the holder of a new tx or evidence | announce items by hash |
| `fetch` | 11 | `kind`, `hashes` | a peer lacking some of them | ask for items (the node caps and deduplicates to 256) |
| `item` | 12 | `kind`, `data` bytes | the holder | the item's bytes |
| `itemNotFound` | 13 | `kind`, `hash` | the holder | it no longer has the item |
| `proposal` | 20 | `Proposal` | the proposer, and re-senders | consensus, pushed |
| `vote` | 21 | `Vote` | validators | consensus, pushed |
| `blockRequest` | 30 | `height` | consensus (a block it saw +2/3 precommits for), backfill, state sync | one block with its commit |
| `blockResponse` | 31 | `height`, `block?`, `commit?` | any node | the stored block or nulls |
| `blocksRequest` | 32 | `from` u64, `count` u32 | block sync | a run of consecutive blocks |
| `blocksResponse` | 33 | `from`, `blocks` [{block, commit}] (≤ 64) | any node | as many consecutive blocks as it has, up to 64 |
| `headerRequest` | 34 | `height` | the light client inside state sync | a header and its commit |
| `headerResponse` | 35 | `height`, `header?`, `commit?` | any node | the stored header and commit |
| `headersRequest` | 46 | `height` u64, `count` u32 | state sync, for the headers below its snapshot height that evidence may still name | consecutive headers downward from `height`, without commits |
| `headersResponse` | 47 | `height`, `headers` Header[] (≤ 1000) | any node | `height`, `height - 1`, ... as far as it holds them, from stored blocks or from headers kept alone, at most `min(count, MAX_HEADERS)` |
| `validatorSetRequest` | 36 | `hash` | light client, backfill | a validator set by hash |
| `validatorSetResponse` | 37 | `hash`, `set?` | any node | the set, without meaningful priorities |
| `validatorsRequest` | 38 | `height` | state sync | the exact set that signs a height, priorities included |
| `validatorsResponse` | 39 | `height`, `set?` | any node | from the store's by-height index |
| `snapshotsRequest` | 40 | none | state sync | which snapshot heights the peer offers |
| `snapshotsResponse` | 41 | `heights` u64[] (≤ 64) | a node running the core app | available snapshot heights |
| `manifestRequest` | 42 | `height` | state sync | the snapshot manifest |
| `manifestResponse` | 43 | `height`, `manifest?` bytes | a node with that snapshot | the encoded manifest |
| `chunkRequest` | 44 | `height`, `objectType` u16, `index` u32 | state sync workers | one chunk |
| `chunkResponse` | 45 | `height`, `objectType`, `index`, `chunk?` bytes | a node with that snapshot | the encoded chunk |

Codes 14 to 19 and 22 to 29 are unused gaps that leave room for new control and consensus messages. The header batch pair was added after the snapshot messages and took 46 and 47 rather than a place next to 34 and 35, which would have renumbered every message after them. The `?` fields are written with `w.option` and read with `r.option`, a presence byte followed by the value.

The decoder is strict. `decodeMessage` rejects an unknown type byte, and every variable-length field carries a limit (`r.string(256)` on hello fields, `r.array(..., 10_000)` on inventory hashes, `64` on block batches and snapshot heights, `MAX_HEADERS` on header batches) so a peer cannot make the receiver allocate without bound. The codec's `decode` also fails if bytes are left over, so a frame must be exactly one message. A decoding failure is reported by the network as a `malformed message` offence worth 20 points.

### src/p2p/peerdb.ts

Known addresses and what happened when they were dialled. The file comment names the model: "Modelled on Graphene's potential_peer_db: the connect loop draws candidates from here, preferring addresses that have worked before and backing off exponentially from ones that have not."

**`PeerRecord`**: `addr`, `lastSeen`, `lastAttempt`, `failures`, `successes`, and optionally `bannedUntil` and `bans`. Times are `Date.now()` milliseconds.

**`PeerDb`**:

- `constructor(file, seeds)`: loads the JSON file if it exists, then adds the seed addresses. With `file = null` nothing is persisted (every test and the localnet script do this).
- `static isValidAddr(addr)`: `host:port` with no whitespace or extra colons in the host, or a bracketed IPv6 literal with a port. Addresses from peers go through this before being stored.
- `add(addr)`: inserts a fresh record; returns false if invalid, already known, or the database already holds `MAX_RECORDS` (4096) addresses. Address exchange is gossip from strangers, and a stranger must not be able to grow a file on disk without bound; a database of a few thousand addresses is already far more than the connect loop will ever dial. `addAll` loops.
- `all()`, `size`.
- `markAttempt(addr)`: stamps `lastAttempt`. `markSuccess(addr)`: increments `successes`, resets `failures` to zero, stamps `lastSeen`, saves. `markFailure(addr)`: increments `failures`, saves.
- `ban(addr, baseMs, now)`: creates the record if needed, increments `bans`, sets `bannedUntil = now + baseMs * 2 ** (bans - 1)`, saves, returns the deadline. The doubling is the "a repeat doubles the time" rule of RPC-SYNC-PROOFS.md 4.6. `isBanned(addr, now)` reads it.
- `candidates(exclude, now)`: the addresses worth dialling now, best first.
- `sample(n, exclude)`: addresses to hand to other nodes.
- `save()`: writes the whole list as JSON, synchronously, when a file was given.

```ts
  candidates(exclude: Set<string>, now = Date.now()): string[] {
    return this.all()
      .filter((r) => !exclude.has(r.addr))
      .filter((r) => now - r.lastAttempt >= Math.min(MAX_BACKOFF_MS, 1000 * 2 ** r.failures))
      .filter((r) => r.bannedUntil === undefined || r.bannedUntil <= now)
      .sort((a, b) => a.failures - b.failures || a.lastAttempt - b.lastAttempt)
      .map((r) => r.addr);
  }
```

The backoff is one second doubled per consecutive failure, capped at `MAX_BACKOFF_MS = 60_000`. A fresh record (`lastAttempt = 0`, `failures = 0`) is eligible at once. Ordering prefers fewer failures, then the least recently attempted, so the loop rotates through addresses instead of hammering one.

```ts
  /** Addresses to share with others: ones that have worked, most recently seen first. */
  sample(n: number, exclude: Set<string>): string[] {
    return this.all()
      .filter((r) => !exclude.has(r.addr) && r.successes > 0)
      .sort((a, b) => b.lastSeen - a.lastSeen)
      .slice(0, n)
      .map((r) => r.addr);
  }
```

Only addresses that have actually worked are shared, which keeps a bad address from spreading through address exchange. One oddity to notice: the doc comment "Addresses worth dialing now, best first." sits above `ban` instead of `candidates`, a leftover from an edit.

### src/p2p/network.ts

The peer manager. It owns the handshake, the peer map, the control messages, the connect and keepalive loops, duplicate resolution and scoring.

**`NetworkConfig`**: `chainId`; `nodeKey` (a `KeyPair`); `transport`; `listenAddr` (`null` to accept nothing); `advertiseAddr` (what to tell peers, defaults to `listenAddr`, then `''`); `peerDb`; `verifier` (the signature verifier, so handshake verification can run on the worker pool); `getHeight` (a function, because the height changes); `log`; and the tunables `desiredOutbound` (8), `maxInbound` (32), `connectIntervalMs` (1000), `pingIntervalMs` (10,000), `idleTimeoutMs` (45,000), `handshakeTimeoutMs` (10,000), `userAgent` (`'crosschain/0.1'`).

**`Peer`**: what the rest of the node sees of a connection after the handshake. `id` (hex node id), `publicKey`, `remoteAddr`, `listenAddr` (from its hello; `''` if it does not listen), `direction` (`'in'` or `'out'`), `height` (updated by every `status`), `latencyMs` (updated by every pong), `lastRecv`, `connectedAt`, `send(message)` and `close()`.

**Constants.** `STALE_DUPLICATE_MS = 2000`, `BAN_THRESHOLD = 100`, `BAN_MS = 3_600_000`, `MAX_HELD_FRAMES = 64`.

**`Network`** public surface:

- `id`: this node's id, `toHex(addressOf(nodeKey.publicKey))`.
- `peers`: `Map<id, Peer>`, readable by everyone (block sync iterates it to pick peers; the RPC lists it).
- `on(type, handler)`: subscribe to a message type. Several handlers per type are allowed; they run in registration order after the network's own control handling.
- `onPeer(fn)`, `onPeerGone(fn)`: lifecycle listeners.
- `start()`: listens if `listenAddr` is set, starts the two loops (unref'd so they do not keep the process alive), and runs the connect loop once immediately.
- `stop()`: stops the loops, closes connections still in handshake, closes every peer, closes the transport.
- `outboundCount`, `inboundCount`.
- `broadcast(message, exceptPeerId)`: `send` to every peer but one. The message is encoded once per peer inside `Peer.send`.
- `connect(addr)`: dial and handshake; resolves with the peer or rejects. Marks the attempt, success or failure in the peer database. Rejects at once if that address is already being dialled. On any failure after the dial succeeded (a rejected or timed-out handshake, a bad signature, the network stopping) it closes the connection: "a connection that did not become a peer is not kept". Otherwise the socket would stay open with no `Peer` to close it, leaking a descriptor here and holding an inbound slot on the other side for a ghost.
- `score(peerId, points, reason)`, `scoreOf(peerId)`, `isBanned(peerId)`.

#### The handshake, message by message

`makeHello()` builds a hello with a fresh nonce from `randomBytes`, the advertise address and the current height. `vetHello(h)` performs the checks common to both directions and returns a reject code or null:

```ts
  private vetHello(h: Hello): { code: number; reason: string } | null {
    if (h.chainId !== this.cfg.chainId) return { code: RejectCode.WrongChain, reason: 'wrong chain id' };
    if (h.publicKey.length !== PUBLIC_KEY_SIZE) return { code: RejectCode.Invalid, reason: 'bad public key' };
    if (bytesEqual(h.publicKey, this.cfg.nodeKey.publicKey)) return { code: RejectCode.Self, reason: 'connected to self' };
    const until = this.bannedIds.get(toHex(addressOf(h.publicKey)));
    if (until !== undefined && until > Date.now()) return { code: RejectCode.NotAccepting, reason: 'banned' };
    return null;
  }
```

`reject(conn, code, reason)` sends a `reject` and closes the connection 50 ms later, long enough for the frame to leave. Closing immediately would, on TCP, often destroy the socket before the reject was written.

Call A the dialer and B the acceptor.

1. **A sends `hello`.** `handshakeOutbound` is called from `connect` once `transport.dial` resolves. It sends `hello_A` and awaits the next message with `nextMessage(conn, handshakeTimeoutMs)`.

2. **B receives `hello`.** The transport's listen callback calls `acceptInbound`. It closes the connection unread if `pendingInbound`, the number of inbound handshakes in flight, is already at `maxInbound` ("more handshakes in flight than peers allowed: not worth even reading"), otherwise counts this one in `pendingInbound` for the duration of the handshake and calls `handshakeInbound`. That awaits the first message; anything but a `hello` is a handshake error. It runs `vetHello`; a failure sends `reject` and throws. If `inboundCount + pendingInbound - 1 >= maxInbound` (the established inbound peers plus every *other* handshake in progress) it rejects with `NotAccepting`, "inbound slots full". Counting the handshakes in progress is what makes the cap hold under a burst: a check against `inboundCount` alone would let a hundred dials that arrive within one handshake's duration each see an empty table, and every one of them would then become a peer. Otherwise it builds `hello_B`, computes `signBytes = handshakeSignBytes(hello_A, hello_B)`, signs them with the node key under the `p2p` context, and sends `helloAck { hello: hello_B, signature }`. Then it awaits the next message.

3. **A receives `helloAck`.** A `reject` here throws with the peer's reason (the test `rejects a peer on another chain` expects `/wrong chain/` from exactly this path). Anything other than `helloAck` is an error. A runs `vetHello` on `hello_B` (so A also refuses a wrong chain, itself, or a banned id), recomputes the same `signBytes`, and verifies B's signature with `verifier.verifyOne`:

```ts
    const signBytes = handshakeSignBytes(helloA, m.hello);
    const ok = await this.cfg.verifier.verifyOne({ sig: m.signature, msg: signBytes, publicKey: m.hello.publicKey, context: this.p2pCtx });
    if (!ok) {
      this.reject(conn, RejectCode.Invalid, 'bad handshake signature');
      throw new HandshakeError('bad handshake signature');
    }
    conn.send(encodeMessage({ type: 'auth', signature: sign(signBytes, this.cfg.nodeKey.secretKey, this.p2pCtx) }));
    return this.establish(conn, m.hello, 'out', addr);
```

A sends `auth` and is established immediately. From this instant A may send anything.

4. **B receives `auth`.** B verifies A's signature over the same bytes with `hello_A.publicKey`. On success it calls `establish(conn, hello_A, 'in', null)`.

The asymmetry in step 3 and 4 is the point of `heldFrames`. A is a peer the moment it sends `auth` and, in the node, immediately sends `addrRequest`, `status` and whatever block sync wants. B is still inside `await verifyOne(...)`, which on a busy worker pool can take a while. Finding 33 of the review describes what happened before: B's connection had no frame handler during that window, so A's first request was dropped and block sync waited out a five-second timeout. The fix is in `nextMessage`:

```ts
    const cleanup = () => {
      clearTimeout(timer);
      // Until the next handshake step or establishment takes over, keep what the other side sends.
      conn.onFrame((frame) => {
        const held = heldFrames.get(conn) ?? [];
        if (held.length < MAX_HELD_FRAMES) held.push(frame);
        heldFrames.set(conn, held);
      });
    };
```

After each handshake message is consumed, the connection's handler is replaced by one that stores frames in a per-connection list (a `WeakMap` keyed by `Conn`, at most 64 frames). The next `nextMessage` first looks in that list, because the next handshake step may already have arrived while a signature was being verified; and `establish` drains the list through the normal `onFrame` path once the peer exists. Frames past the 64th are silently dropped, which bounds what an unauthenticated connection can make the node hold. The test `delivers a message sent the instant a peer connects, while the other side is still verifying the handshake` wraps the verifier so `verifyOne` sleeps 100 ms, sends a `status` from `onPeer` on the dialing side, and asserts it arrives.

`nextMessage` also rejects with `handshake timeout` after `handshakeTimeoutMs`, with `closed during handshake` if the connection closes, and with `bad handshake message` if the frame does not decode. All are `HandshakeError`s; `connect` logs them at debug level and marks the address as failed in the peer database; `acceptInbound` logs and closes.

#### Establishing a peer and resolving duplicates

`establish(conn, their, direction, dialedAddr)` first refuses if the network has stopped meanwhile. It builds the `Peer` object, with `send` guarded by `conn.closed` and `close` that closes the connection and removes the peer. Then it checks for an existing peer with the same id:

```ts
    const existing = this.peers.get(id);
    if (existing) {
      const stale = Date.now() - existing.connectedAt > STALE_DUPLICATE_MS;
      const iAmLower = this.id < id;
      const newIsCanonical = (direction === 'out') === iAmLower && existing.direction !== direction;
      if (!stale && !newIsCanonical) {
        this.cfg.log('debug', 'dropping duplicate connection', { peer: id.slice(0, 8), direction });
        conn.close();
        throw new HandshakeError('duplicate connection');
      }
      this.cfg.log('debug', 'replacing duplicate connection', { peer: id.slice(0, 8), direction, stale });
      existing.close();
    }
```

Work through a simultaneous dial between X (lower id) and Y. On X, the outbound connection to Y and the inbound one from Y both arrive within milliseconds. Suppose X's inbound one is established first. When the outbound one is established, `direction === 'out'`, `iAmLower` is true, the existing one is `'in'`, so `newIsCanonical` is true: the new (outbound, initiated by the lower id) replaces the old. If instead X's outbound one came first, the inbound one arrives with `direction === 'in'`, `(false) === true` is false, `newIsCanonical` is false, and it is dropped. On Y, the mirror image: Y is not lower, so the connection *initiated by X*, which is Y's inbound one, is canonical. Both sides keep the same connection without exchanging a word about it. The test `a simultaneous dial leaves exactly one connection on each side` runs this with 20 ms of latency and checks that the surviving connection has opposite directions on the two sides.

If the existing connection is more than two seconds old, it is assumed stale (the peer restarted, and its old socket has not timed out) and the new one replaces it regardless of direction. DESIGN.md section 3 explains why: "a restarted validator rejoins at once instead of waiting for the old socket to time out."

Then the peer is installed:

```ts
    this.peers.set(id, peer);
    conn.onFrame((frame) => this.onFrame(peer, frame));
    conn.onClose(() => this.removePeer(peer));
    if (their.listenAddr) this.cfg.peerDb.add(their.listenAddr);
    if (dialedAddr) this.cfg.peerDb.markSuccess(dialedAddr);
    this.cfg.log('info', 'peer connected', { peer: id.slice(0, 8), direction, addr: their.listenAddr || conn.remoteAddr, height: their.height });

    peer.send({ type: 'addrRequest' });
    peer.send({ type: 'status', height: this.cfg.getHeight() });
    for (const fn of this.peerListeners) fn(peer);
    const held = heldFrames.get(conn);
    heldFrames.delete(conn);
    if (held) for (const frame of held) this.onFrame(peer, frame);
    return peer;
```

The order matters: `onPeer` listeners run before held frames are delivered, so a listener that sends a request (block sync does, on `onPeer`) has registered its expectations before any early response is processed; and the peer's own first `status` goes out before anything else so the other side's block sync knows this node's height at once.

#### The life of a peer

Every frame from an established peer goes through `onFrame`:

```ts
  private onFrame(peer: Peer, frame: Uint8Array): void {
    let m: Message;
    try {
      m = decodeMessage(frame);
    } catch (e) {
      this.cfg.log('warn', 'undecodable message', { peer: peer.id.slice(0, 8), err: (e as Error).message });
      this.score(peer.id, 20, 'malformed message');
      return;
    }
    peer.lastRecv = Date.now();
    this.handleControl(peer, m);
    const list = this.handlers.get(m.type);
    if (list) for (const h of list) h(peer, m);
  }
```

`handleControl` is the network's own handling, and it runs *before* the subscribers, which is why `peer.height` is already updated when block sync's `status` handler reads it:

- `ping` is answered with a `pong` echoing the time; `pong` sets `latencyMs = now - time`.
- `status` sets `peer.height`.
- `addrRequest` is answered with the listen addresses of every current peer (excluding the asker's own and this node's) plus up to 16 from `peerDb.sample`, capped at 32 entries.
- `addrResponse` adds every address except this node's own advertise address to the peer database. The database validates them.
- `hello`, `helloAck` or `auth` after the handshake means a confused or hostile peer: it is dropped.
- `reject` after the handshake closes the peer.

Subscribers also see `ping`, `status` and the rest; nothing is hidden from `on`.

`removePeer` is idempotent (it checks that the map still holds this exact `Peer` object, so a replaced duplicate does not remove its replacement) and notifies `onPeerGone` listeners, which is how the `Requester` fails pending requests and block sync forgets a peer's height.

**The connect loop** runs every `connectIntervalMs`:

```ts
  private connectLoop(): void {
    if (!this.running) return;
    const need = this.cfg.desiredOutbound - this.outboundCount - this.dialing.size;
    if (need <= 0) return;
    const exclude = new Set<string>([this.cfg.advertiseAddr, ...this.dialing]);
    // Addresses we dialed are taken; an inbound peer's advertised address is only a claim and must not stop us dialing it.
    for (const p of this.peers.values()) if (p.direction === 'out') exclude.add(p.remoteAddr);
    for (const addr of this.cfg.peerDb.candidates(exclude).slice(0, need)) void this.connect(addr).catch(() => {});
  }
```

It tops up outbound connections only. The exclusion set holds exactly the addresses this node knows to be taken: its own advertise address, the dials in flight, and the remote address of every *outbound* peer, which is the address that was dialled. An inbound peer's advertised `listenAddr` is deliberately not in it. That address is whatever the peer wrote in its hello, and a hostile inbound peer could advertise the address of an honest seed; if advertised addresses excluded candidates, a few such connections could remove every configured seed from the dial list and leave the node with only the peers the attacker chose, which is the eclipse the outbound slots exist to prevent. The price is small: the node may dial a node it is already connected to inbound, and the duplicate-connection rule in `establish` then keeps exactly one of the two. Failures are swallowed here; `connect` has already logged and recorded them.

**The keepalive loop** runs every `pingIntervalMs`. A peer whose `lastRecv` is older than `idleTimeoutMs` is closed with the log line `dropping idle peer`; every other peer is pinged. The default idle timeout, 45 s, is 4.5 ping intervals, so a few lost pongs do not drop a peer.

#### Scoring

```ts
  score(peerId: string, points: number, reason: string): void {
    const now = Date.now();
    const s = this.scores.get(peerId) ?? { points: 0, last: now };
    s.points = Math.max(0, s.points - (now - s.last) / 60_000) + points;
    s.last = now;
    this.scores.set(peerId, s);
    this.cfg.log('debug', 'peer scored', { peer: peerId.slice(0, 8), points, total: Math.round(s.points), reason });
    if (s.points < BAN_THRESHOLD) return;
    this.scores.delete(peerId);
    const peer = this.peers.get(peerId);
    // Only an address we dialed is known to be this peer's; an advertised one could be anybody's.
    const addr = peer?.direction === 'out' ? peer.remoteAddr : null;
    const until = addr ? this.cfg.peerDb.ban(addr, BAN_MS, now) : now + BAN_MS;
    this.bannedIds.set(peerId, until);
    this.cfg.log('warn', 'peer banned', { peer: peerId.slice(0, 8), reason, untilMs: until - now });
    peer?.close();
  }
```

Decay is applied lazily, at the moment of the next charge, as `(elapsed minutes)` points. At the threshold the node id goes into `bannedIds` (checked by `vetHello` on every future handshake in either direction), the peer is closed, and, only for an outbound peer, the address this node dialled goes into the peer database's ban list (checked by `candidates`, so the connect loop will not dial it). An inbound peer gets no address ban: its remote address is an ephemeral port nobody will dial, and its advertised `listenAddr` is a claim the node never verified. Banning a claimed address would hand a hostile peer a way to get an honest node's address banned here, by advertising it and then misbehaving. `bannedIds` lives in memory only; the address ban is persisted with the peer database. `scoreOf` reports the decayed total without charging, which `test/sync.test.ts` uses to confirm that a joiner charged a peer for a corrupt chunk (`toBeGreaterThan(40)`: 50 points minus a moment of decay).

The network charges only for frames that do not decode. The other tariffs are charged by callers: the node for malformed or invalid evidence and oversized fetches, consensus for bad signatures, sync for bad blocks, manifests and chunks.

### src/p2p/request.ts

A promise interface over a protocol without request ids.

```ts
const RESPONSE_TYPES: MessageType[] = ['blockResponse', 'blocksResponse', 'headerResponse', 'headersResponse', 'validatorSetResponse', 'validatorsResponse', 'snapshotsResponse', 'manifestResponse', 'chunkResponse', 'addrResponse'];
```

**`Requester`**: the constructor subscribes to every response type and to `onPeerGone`, so a disconnect fails every request pending on that peer with `peer disconnected`.

```ts
  request<T extends MessageType>(peer: Peer, msg: Message, responseType: T, match: (m: Of<T>) => boolean, timeoutMs = 5000): Promise<Of<T>> {
    return new Promise<Of<T>>((resolve, reject) => {
      const p: Pending = {
        peerId: peer.id,
        type: responseType,
        match: (m) => match(m as Of<T>),
        resolve: (m) => resolve(m as Of<T>),
        reject,
        timer: setTimeout(() => this.settle(p, new Error(`${responseType} from ${peer.id.slice(0, 8)} timed out`)), timeoutMs),
      };
      this.pending.push(p);
      try {
        peer.send(msg);
      } catch (e) {
        this.settle(p, e as Error);
      }
    });
  }
```

`request(peer, msg, responseType, match, timeoutMs)` registers a pending entry, sends the message, and resolves with the first message of `responseType` from that peer that satisfies `match`, or rejects on timeout. The pending entry is pushed *before* `send`, so the matching does not depend on how quickly a transport delivers: both transports deliver asynchronously (the memory hub through `setTimeout`, even at zero latency), but registering first makes the order irrelevant. `deliver` finds the first pending entry by peer, type and predicate; `settle` removes it, clears the timer and resolves or rejects. `inflight` reports the pending count.

Because responses are matched by predicate, a caller must choose predicates that identify its request: block sync matches `blocksResponse` on `from`, state sync matches `chunkResponse` on height, type and index. Two identical concurrent requests to one peer would be satisfied in order by the two responses, which is correct. A response nobody asked for simply matches nothing and is ignored by the requester; other subscribers to the same type still see it. That is how the node's `blockResponse` handler for consensus (see [the node](08-node.md)) and block sync's backfill coexist on one message type: consensus ignores responses whose height is not its current height, and the requester ignores responses no pending request matches.

The `try/catch` around `peer.send` is defensive; `Peer.send` as written never throws (it checks `conn.closed` and both transports' `send` return silently when closed). A request to a closed peer therefore waits for its timeout unless `onPeerGone` has already fired, which it has if the peer was removed.

## How it is tested

`test/network.test.ts` builds bare `Network` objects (no node) with fast intervals (`connectIntervalMs: 50`, `pingIntervalMs: 200`, `idleTimeoutMs: 1000`) and an inline verifier.

- `handshakes, exchanges status and addresses, and pings`: three nodes where `b` seeds only `a` and `c` seeds only `b`. All three end up with two peers each, which proves address exchange: `c` learns `a`'s address from `b`'s `addrResponse`. It also checks that `b` recorded `a`'s height (7) and listen address from the hello, that latency has been measured and that `lastRecv` is fresh, which proves the keepalive is running.
- `delivers a message sent the instant a peer connects, while the other side is still verifying the handshake`: the regression test for finding 33 described above. A slow `verifyOne` on the acceptor and a `status` sent from the dialer's `onPeer`; the message must arrive.
- `rejects a peer on another chain and a connection to itself`: `b.connect('a:1')` across chain ids rejects with `wrong chain` (the reject travels from the acceptor's `vetHello` to the dialer's `handshakeOutbound`); `a.connect('a:1')` rejects with `self`; no peer remains.
- `a simultaneous dial leaves exactly one connection on each side`: both sides dial at once with 20 ms latency; at least one `connect` fulfils, after 200 ms each side has exactly one peer, and the directions are opposite, proving both sides chose the same connection.
- `drops a peer that goes silent`: after connecting, the hub partitions the pair; `a` drops `b` within the idle timeout.
- `handshakes over real sockets and delivers framed messages` (the `p2p over TCP` group): two `TcpTransport`s on localhost, a handshake over real sockets, a `status` message delivered through the framer, and the hello height recorded.

`test/review2.test.ts`, `bounds the peer database and refuses an unnamed key`, feeds `MAX_RECORDS + 50` distinct addresses to a `PeerDb` and asserts that exactly `MAX_RECORDS` were accepted and `size` stops there.

Elsewhere, `test/sync.test.ts` checks `Network.scoreOf` after a peer served a corrupt chunk, and every consensus and sync test drives the whole stack through the memory transport, including partitions (`halts during a partition and resumes without divergence after healing` in `test/consensus.test.ts`) and a message filter that drops proposals for one node.

## Limitations and ideas

Known simplifications, from DESIGN.md section 10 and from reading the code:

- No encryption. Everything that matters is signed, but an observer sees every transaction and vote in the clear.
- Vote verification is not rate limited per peer (DESIGN.md section 10). A peer can make a node verify many signatures before it accumulates enough points to be banned.
- `ping`/`pong` yields latency only; DESIGN.md section 3 also wanted a clock offset per peer, which REVIEW-2026-10-28.md ("Found while documenting") records as left for later.
- The peer database keeps last seen and the success and failure counts; DESIGN.md section 3 notes that "the outcome enumeration was not needed". `RejectCode.AlreadyConnected` is never sent; `bannedIds` are not persisted across restarts while banned addresses are.
- The optional reachability check ("ask a peer to connect back to the advertised endpoint") is deferred.
- `broadcast` encodes the message once per peer.

Exercises:

1. Add a clock offset to `Peer`, computed from the pong's echoed time and the local time at send and receive, and log peers whose clocks are far off.
2. Persist `bannedIds` next to the peer database so a restart does not forget bans by node id.
3. Encode a broadcast once: have `Network.broadcast` call `encodeMessage` a single time and give `Conn.send` the bytes directly, keeping `Peer.send` for single sends.
4. Write a unit test for the TCP framer alone: feed `TcpConn.onData` a frame split across many one-byte chunks, and two frames in one chunk, and assert both are delivered intact.
5. Implement the reachability check from DESIGN.md: a `connectBack` request, a dial by the peer to the advertised address, and a flag on the peer record.
6. Add per-peer rate limiting for `vote` and `proposal` messages at the network layer, charging points when a peer exceeds it.
